## How to read this

**Requests first, latency second.** Cost and latency in this project are both driven by object-store
requests. Request counts are deterministic (same code + same dataset ⇒ same count) and can gate a PR;
latency depends on the machine and is advisory only.

**Cold and warm are separate columns.** Warm numbers look great because the data is already in memory;
the cold column is what the object store actually costs you.

## Reproduce

```bash
./gradlew :yb-bench:benchPublic \
  -PYB_BENCH_PROFILE=default -PYB_BENCH_OUT=bench/current.json
scripts/bench-compare.py --baseline bench/baseline-<profile>.json \
                         --current bench/current.json
```

Point the harness at a real bucket with `-PYB_S3_ENDPOINT` / `YB_S3_ACCESS_KEY` / `YB_S3_SECRET_KEY`; the default is an in-process S3-compatible server, which keeps the numbers about YangBase itself rather than about network jitter.

## What gates a pull request

- **Hard failure:** `requestsPerOp` / `bytesPerOp` / storage footprint regress by more than 5%. These are deterministic, so a failure there is a real regression.
- **Exception — concurrent writes:** batch sizes depend on thread scheduling, so the ratio moves between machines without any code change (first CI run: 0.188 → 0.212 with identical code). It is gated by an *invariant* instead: averaged requests per transaction must stay ≤ 1.
- **Warning only:** p50/p95/p99 latency regresses by more than 5% (with a 200 µs noise floor). Shared CI runners cannot support a hard latency gate; pretending otherwise just gets the gate disabled.
- **Excluded:** anything that needs a real cloud backend (OSS/COS/OBS/R2/B2 latency profile). Those numbers live in the conformance reports, not here.
