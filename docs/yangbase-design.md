## 0. 文档说明

### 0.1 阅读对象

本文档面向：(a) 参与实现的工程师，用于确认接口契约与模块边界；(b) 架构评审者，用于挑战关键取舍；(c) 潜在使用者，用于判断特性是否满足业务需求。

**建议的评审顺序**：先读 §1（问题定义）和 §16（风险与开放问题）——它们定义了本文档的边界与不确定性；再读 §5（对象存储布局），它是整个系统最核心、最难改的设计；最后按兴趣深入其余章节。

### 0.2 术语表

| 术语 | 含义 |
|---|---|
| **对象存储** | 提供 S3 风格 API 的存储服务（AWS S3、阿里云 OSS、腾讯云 COS、MinIO、Cloudflare R2 等）。注意与阿里云 OSS 的同名混淆，本文正文一律称"对象存储"。 |
| **CN (Compute Node)** | 计算节点。无状态，承载 SQL 解析、优化、执行、存储引擎与缓存。 |
| **MS (Meta Service)** | 元数据服务。3 节点 Raft 小组，提供 TSO、租约、锁、Catalog。状态持久化在对象存储上。 |
| **Shard（分片）** | 存储与写入的最小单元，粒度是 `(表, 分区)`。每个分片在任一时刻只有一个写者。 |
| **Manifest（清单）** | 描述一个分片当前所有数据文件的不可变元数据对象，是 LSM 的"根指针"。 |
| **SST** | Sorted String Table，LSM 中不可变的有序数据文件。 |
| **WAL** | Write-Ahead Log，写前日志。本文中特指存储在对象存储上的、由多个小对象组成的日志流。 |
| **TSO** | Timestamp Oracle，全局单调递增时间戳分配器。 |
| **Epoch / Fencing Token** | 写者租约的代际编号，单调递增，用于隔离已被罢免的旧写者。 |
| **MVCC** | 多版本并发控制。每一行版本携带 `commit_ts`。 |
| **段 (Segment)** | 全文/倒排索引中一次构建产出的不可变索引单元，类比 Lucene segment。 |

### 0.3 设计目标与非目标

**目标（本次设计必须达成的）：**

| # | 目标 | 可度量的验收标准 |
|---|---|---|
| G1 | 全部持久状态落在对象存储 | 任何 CN 与 MS 进程被强杀后，除对象存储外不依赖任何本地状态即可恢复；本地磁盘只允许作为可丢弃缓存 |
| G2 | 计算节点无状态 | CN 可随时增删；新 CN 冷启动到可服务 < 5s，无需数据搬迁 |
| G3 | 把成本从"与实例存活时间绑定"变为"与实际使用量绑定" | 与**数据量**绑定的月度成本降低 ≥ 30×；与**计算**绑定的成本可降至 0（实例可随时停）；量化见 §13 |
| G4 | 兼容 MySQL 协议 | 现有 JDBC / MyBatis / mysqldump / Navicat / DataGrip 无需改造即可连接 |
| G5 | 支持完整的事务语义 | 默认 REPEATABLE READ（快照隔离），支持跨分片事务 |
| G6 | 多模索引 | 主索引、二级有序索引、哈希索引、跳数索引、全文/倒排索引 |
| G7 | 支持数据分区 | 分区裁剪 + 分区作为并行写入单元 |
| G8 | 可长期低成本运行 | 空闲时对象存储请求数趋近于 0；无强制常驻的高规格实例 |

**非目标（明确不做，避免设计蔓延）：**

- **N1：不追求替代 OLTP 高并发核心库。** 单分片写路径的下界是对象存储往返延迟，本系统定位于**读多写少、写入 QPS 在数百到数千**的场景（SaaS 后台、内容站、IoT 元数据、初创产品）。高写入场景通过分区获得横向扩展，但单个分区的写入延迟无法低于一次对象存储 PUT。
- **N2：不实现 MySQL 的全部生态。** 存储过程、触发器、事件调度器、`SELECT ... INTO OUTFILE` 等不在范围内（§11.3 有完整清单）。
- **N3：不做跨 Region 强一致。** 跨 Region 只提供异步只读副本。
- **N4：不做列存 / OLAP 引擎。** 虽有列式段结构服务于索引，但查询执行是行式向量化的，不追求分析型查询性能。
- **N5：不保证 P99 延迟与本地盘数据库同级。** 对象存储的尾延迟（p99 可达数百毫秒）是无法消除的物理约束，只能通过缓存把稳态命中率做高。

| # | 决策 | 选择 | 备选与代价 | 章节 |
|---|---|---|---|---|
| D1 | 协调模型 | **双模式，部署时选择**（Q2）：轻量常驻元数据服务（Raft×3，多 CN 的推荐模式）**或** 纯对象存储 CAS（零常驻成本） | 只做其中一种：要么失去零常驻成本的部署选项，要么每次提交多 1–2 个 RTT | §4、§4.7 |
| D2 | 数据持久层 | **对象存储为唯一真相源** | 本地盘做真相源：失去存算分离与弹性 | §3 |
| D3 | 写路径 | **单写者日志流 + LSM** | 多写者 delta 合并：写延迟更低，但提交顺序判定与读放大复杂度陡增 | §6.3 |
| D4 | WAL 形态 | **多小对象顺序日志 + 后台合并成段** | S3 Multipart 追加：part 最小 5 MiB，低延迟场景不可用 | §6.3.3 |
| D5 | 提交延迟 | **默认组提交（group commit）**，可按表切换三档 | 每事务一次 PUT：延迟可控但请求费用与吞吐不可接受 | §6.3.4 |
| D6 | SST 布局 | **索引块与数据块分离成两个对象** | 单文件 + 字节范围读：点查省一次 GET，但索引无法整体常驻内存 | §6.4 |
| D7 | 事务协议 | **MVCC(快照隔离) + 单分片串行 + 跨分片 2PC（Percolator 式 primary record）** | 纯 OCC：冲突重试率高 | §7 |
| D8 | 索引统一抽象 | **一切索引 = 不可变文件 + manifest 指针** | 各异构实现：无法共享缓存/GC/备份逻辑 | §8.1 |
| D9 | B+ 树索引 | **以 LSM 实现，对外提供 B+ 树访问语义** | 真·COW B+ 树：范围扫描更优雅，但点查需要 3–4 次 GET | §8.3 |
| D10 | 全文索引 | **自研段式倒排索引（Kotlin）** | 内嵌 Lucene/Tantivy：省事但假设本地文件系统，MVCC 集成困难 | §8.6 |
| D11 | 分区角色 | **分区即写入分片**（与 MySQL 语义天然对齐） | 分区仅作逻辑概念：失去并行写入 | §9.3 |
| D12 | 隔离级别 | **默认 REPEATABLE READ = 快照隔离** | 默认 RC：与 MySQL 默认不符，迁移风险 | §7.4 |
| D13 | 构建系统 | **Gradle Kotlin DSL 多模块** | 保留现有 Maven：Kotlin 增量编译与序列化插件体验较差 | §15.3 |
| D14 | Compaction 布局 | **L1 及以下强制 leveled**（层内不重叠、跨层唯一） | tiered/universal：写放大更低，但会**静默破坏 `COUNT(*)` 的精确性**（§8.9.3） | §6.6、§8.9 |

## 1. 背景与问题定义

### 1.1 成本结构：一个被忽视的错配

问题的起点是一个非常真实的成本观察：

1. 云厂商 ECS 按需价格高，但**节假日/大促常有大额折扣**，此时购入长期实例非常划算；
2. 然而**续费价格回归原价**，届时要降本只能重新购入新实例，把旧数据全量迁移后删库；
3. 于是每一次"续费周期"都变成一次**被迫的停机与全量搬迁**，服务的可用性被基础设施的计费周期绑架。

对初创应用而言这个错配更尖锐：**没有多少客户时，用昂贵的 ECS 维持一个传统 DB 来存储少量数据，是极不划算的**。

这里的关键洞察是：**数据的价值与数据的量、访问频度是解耦的**。一个只有几千用户的产品，数据可能只有几百 MB，每天几千次读写——但它依然需要事务、索引、SQL 和 MySQL 协议的兼容性。

### 1.2 成本结构对比

| 资源 | 相对单价 | 是否随实例生命周期绑定 | 特点 |
|---|---|---|---|
| 计算（vCPU/内存） | 高，且随规格台阶跳变 | **是** —— 停机即省钱 | 可弹性、可抢占、可按需起停 |
| 块存储（云盘） | 中 | 是 —— 挂载在实例上 | 生命周期与实例绑定，迁移需要快照 |
| 对象存储 | **极低**（约块存储的 1/3 ~ 1/6 每 GB，且无最低消费） | **否** —— 独立于计算 | 按量付费、天然多副本、支持生命周期分层、有强一致读 |

这个对比给出了明确的结论：

> **把持久状态从"与计算实例绑定的块存储"中搬出来，放进"与计算解耦的对象存储"**，就同时解决了两个问题：
> (1) 计算层可以完全跟随价格波动迁移，节假日买、到期换，随时销毁重建而无数据损失；
> (2) 低频数据不再需要为"能挂载它的那台昂贵实例"付费。

### 1.3 核心矛盾与本文档的应对

把 OLTP 数据库放在对象存储上，会直面三个物理事实：

| 物理事实 | 影响 | 本文档的应对 |
|---|---|---|
| **对象存储是"对象级"接口，不是块级** | 无法原地更新，一切写都是新建对象 | 全系统采用**不可变对象 + 指针切换**（manifest 模式），写路径退化为"生成新对象 + 原子换指针" |
| **RTT 高（同一 Region 内约 10–60ms，尾部可达数百 ms）** | 每次同步写都可能付出一次 RTT | 组提交摊薄、多级缓存、把元数据对象做小做热、预取 |
| **按请求计费** | 小对象密集访问会让费用失控 | 请求数作为一等性能指标（§14.2），用合并、缓存、批量来压 |

同时，对象存储有三个**常被低估的优势**，本文档会主动利用：

| 优势 | 利用方式 |
|---|---|
| **不可变对象天然适合 MVCC 与时间旅行** | 保留历史 manifest 即获得近乎零成本的 PITR 与 `AS OF TIMESTAMP` 查询（§12.3、§7.6） |
| **高并发读带宽（聚合可达数十 GB/s）** | 大范围扫描用并行 range GET，用带宽换延迟 |
| **强一致读 + 天然多副本** | 不需要自己实现副本复制与一致性协议，RPO=0 由基础设施保证 |

### 1.4 设计原则

以下原则在后续章节中被反复引用，出现冲突时按序号优先：

- **P1 对象存储是唯一的真相源。** 本地磁盘与内存的一切内容必须可丢弃。任何"为了方便而把权威状态放在本地"的设计一律否决。
- **P2 不可变优先。** 凡是可能被并发读的对象，一律不可变；变更通过生成新对象并切换指针表达。可变的只有"指针对象"和元数据服务的内存状态。
- **P3 元数据小且热，数据大且冷。** 元数据对象（manifest、索引块、统计信息）要小到可以整体常驻内存；数据对象只按需做范围读取。
- **P4 请求数是一等成本。** 任何功能设计都要回答"它引入了多少额外对象存储请求"。缓存未命中路径上的请求数按 §14.2 的预算表核算。
- **P5 无状态计算。** CN 不持有任何不可重建的状态。写者身份是租约，不是节点属性。
- **P6 显式降级。** 面对不同对象存储后端的能力差异（是否支持条件写、是否强一致读），通过能力探测 + 显式降级路径处理，而不是假设最低公分母。

**架构的不对称性**（这是 D1 决策的直接后果，评审时应重点关注）：数据面（Data Plane）完全无中心、可弹性伸缩；控制面（Control Plane）有一个 3 节点的小型常驻集群。设计上刻意让控制面**弱**：

- MS 只持有**派生状态**与**短期状态**（TSO 缓存、租约、锁表），其权威状态定期快照到对象存储；
- MS 可以整体被强杀并冷启动，从对象存储快照恢复；
- MS 挂掉时，**只读事务可以继续**（使用预取的 TSO 批次），只有写事务和 DDL 需要等待；
- MS 的实例规格可以极小（2 vCPU / 4 GiB × 3，甚至用抢占实例），其成本在 §13 中量化。

### 2.3 一次点查的完整路径

这条路径是系统的性能基准线，所有优化都围绕它展开。

```
 Client ── COM_QUERY: SELECT * FROM orders WHERE id = 42 ──▶ cn-2
                                                              │
 ① 解析 & 计划：命中主键索引，得到 (table=orders, partition=p3, pk=42)
                                                              │
 ② 读取分片 manifest（缓存优先）                                 │
    ├─ 命中本地 manifest 缓存 ──────────────────────────── 0 次 GET
    └─ 未命中/需校验 → 条件 GET manifest/CURRENT
                        └─ 304 Not Modified ─────────── 0 字节传输
                                                              │
 ③ 定位候选文件：manifest → L0 文件（bloom filter 判定）        │
    ├─ 命中 MemTable ────────────────────────────────── 0 次 IO
    └─ 未命中 → bloom 说"可能在 f_0a3.dat"                      │
                                                              │
 ④ 读取文件索引对象 f_0a3.idx                                  │
    ├─ 已常驻内存（稳态，见 §6.7）────────────────────── 0 次 GET
    └─ 冷启动 → GET f_0a3.idx (~200 KB) ─────────────── 1 次 GET
                                                              │
 ⑤ 得到数据块偏移 [off, off+len)                              │
      GET f_0a3.dat  Range: bytes=off-(off+len-1) ────── 1 次 GET
                                                              │
 ⑥ 在块内二分定位 → 用 read_ts 做 MVCC 可见性判断               │
      → 返回行                                                   │
```

**结论：稳态下，一次点查只需 1 次对象存储 GET（数据块本身），且只传输 4–64 KB。** 这是整个存储层设计的核心目标，§6.4 的"索引/数据分离布局"和 §6.7 的缓存体系都是为了守住这条线。

## 3. 对象存储抽象层

### 3.1 为什么需要能力模型

不同对象存储后端的能力差异很大，而本系统的许多关键路径**依赖特定能力**。如果按最低公分母设计，会白白浪费掉高端后端的性能；如果按最强后端设计，又会在弱后端上悄悄出错。因此引入**显式的能力探测 + 降级**（原则 P6）。

```kotlin
/**
 * 后端能力的声明式描述。在连接建立时探测一次，之后全局只读。
 * 任何依赖某项能力的代码路径都必须先检查，否则视为 bug。
 */
data class ObjectStoreCapabilities(
    /** 支持 If-None-Match: * 的原子创建 */
    val conditionalCreate: Boolean,
    /** 支持 If-Match: <etag> 的原子比较交换 */
    val conditionalUpdate: Boolean,
    /** 读己之写（read-after-write）强一致；S3 自 2020-12 起成立 */
    val strongReadAfterWrite: Boolean,
    /** LIST 的强一致性与有序性 */
    val strongListConsistency: Boolean,
    /** 单对象最大尺寸 */
    val maxObjectSize: Long,
    /** Multipart 分片最小尺寸（S3 为 5 MiB，末片除外） */
    val multipartMinPartSize: Long,
    /** 是否提供低延迟存储层（如 S3 Express One Zone / OSS 传输加速） */
    val lowLatencyTier: Boolean,
    /** 低延迟层是否同样支持条件写。⚠️ S3 Express One Zone 为 false，见 §3.3.1 */
    val lowLatencyTierSupportsConditionalWrite: Boolean,
    /** 条件写是否被后端正确实现（而非静默忽略）。必须用真实的冲突写请求实测，见 §3.3.1 */
    val conditionalWriteVerified: Boolean,
    /** 是否按请求计费（决定请求数优化的紧迫程度） */
    val requestsAreBilled: Boolean,
    /** 是否原生支持服务端拷贝（用于 compaction 时的零流量重写） */
    val serverSideCopy: Boolean,
    /** 是否支持对象变更事件通知（用于缓存失效） */
    val eventNotification: Boolean,
)
```

### 3.2 SPI 定义

SPI 刻意保持**窄**——只有 6 个操作，避免各后端在行为细节上分叉。所有上层逻辑（LSM、索引、GC）都构建在这 6 个操作之上。

```kotlin
interface ObjectStore {
    val caps: ObjectStoreCapabilities

    /** 读取整个对象，或对象的某个字节区间 */
    suspend fun get(key: ObjectKey, range: ByteRange? = null): ObjectData

    /**
     * 写入对象。
     * @param precondition 原子性前置条件；当 caps 不支持而又传入了非空值时，
     *                     实现必须抛出 CapabilityNotSupported，而不是静默忽略。
     */
    suspend fun put(key: ObjectKey, data: ObjectData, precondition: Precondition? = null): ETag

    /** 删除对象（幂等；对象不存在时返回 false） */
    suspend fun delete(key: ObjectKey): Boolean

    /** 按键字典序分页列举；pageToken 为不透明游标 */
    suspend fun list(prefix: String, pageToken: String? = null, limit: Int = 1000): ListPage

    /** 获取元信息（不传输内容），用于条件校验 */
    suspend fun head(key: ObjectKey): ObjectMeta

}

sealed interface Precondition {
    /** If-None-Match: * —— 仅当对象不存在时写入成功（原子创建） */
    object MustNotExist : Precondition
    /** If-Match: <etag> —— 仅当 etag 匹配时写入成功（CAS） */
    data class MustMatch(val etag: ETag) : Precondition
}
```

> **📌 决策记录（2026-09-25，实现后回看）：接口里没有 `compose`。**
>
> 本节初稿把「服务端拼接」（S3 `UploadPartCopy` / OSS `CopyObject`）列为接口的一等方法，
> 设想用来免流量地拼 SST。原型实现过一版（三条路径：服务端拼接、自愈降级、能力探测），
> 审查时逐条走查调用链，结论是**它在当前架构里不可能被用上，而且用了会更贵**：
>
> 1. **没有"可以原样保留的区间"**。§6.6 设想的场景是「L2 合并到 L3 时某个 L2 文件与
>    L3 无重叠」——而当前实现只有 L0/L1 两层（§16.3），compaction 是 L0+L1 → L1，
>    每一个字节都由 `SstWriter` 重新编码；不重叠的 L1 文件本来就**按引用保留**，
>    连拷贝都不发生，比拼接更省。
> 2. **S3 协议不允许小片拼接**。`UploadPartCopy` 要求除最后一片外每片 ≥ 5 MiB，
>    而 WAL 段合并要拼的对象是 KB 级的（§6.3.2）——服务端路径永远走不到，只会落到
>    「下载 + 上传」兜底；兜底还要为每个源多一次 `head` 校验区间，
>    **请求数比现在直接拼接更多**（P4：请求数是一等成本）。
> 3. **没有整对象复制的调用点**。备份/恢复/PITR 都是指针操作（§6.9），
>    写一个 manifest 指针，不搬字节。
>
> 因此接口保持 **5 个操作**（`get`/`put`/`delete`/`list`/`head`）——窄接口让各后端
> 的行为差异面更小，这正是 P6「显式降级」希望的方向。**重新引入的条件**写在这里，
> 免得日后凭印象重做一遍：当且仅当 (a) 实现了 L1 以下的 leveled compaction，
> 且 (b) 合并输入里存在 > 5 MiB 的、需要原样保留的区间时，`compose` 才值得回来。

#### 3.3.1 ⚠️ 关键约束：CAS 与低延迟目前不可兼得

**S3 Express One Zone 的 `PutObject` 不支持条件写**（官方 API 文档明示 *not supported for directory buckets*；只有 `RenameObject` 支持 `If-None-Match: *`）。而它与标准 S3 的延迟差距是数量级的。这给出一个直接推论：

> **不能把事务元数据（manifest 指针）放在低延迟存储层上，也不能指望用低延迟层做写者选举。**

本设计的应对是**分层**——而这个拆分之所以成立，恰恰是因为"**数据对象不可变且名字唯一，因此不需要 CAS**"：

| 对象类别 | 存放层 | 需要 CAS？ | 依据 |
|---|---|---|---|
| **manifest / CURRENT**（提交点） | 标准 S3 | **需要**（`If-Match`） | 接受 100ms 级的提交延迟，已由组提交摊薄 |
| **WAL 对象** | 标准 S3 | 不需要（key 含 epoch + seq，天然唯一） | 与 manifest 同层，避免跨层一致性推理 |
| **SST `.dat` / `.idx`** | **可放 Express One Zone** | 不需要（不可变 + 唯一名） | 纯读路径提速，不影响正确性 |
| **倒排索引段** | 可放 Express One Zone | 不需要 | 同上 |

**正确性论证**：数据对象的创建永远不产生冲突（名字唯一且不可变），条件写只被"提交点"需要；而提交点每批次只有一个，其延迟已被组提交摊薄。于是**低延迟层与 CAS 在物理上被解耦，两者可以同时获得**。

**对阿里云 OSS 的适配**：OSS 无 ETag CAS，因此写者选举**必须完全依赖 MS 的租约**（§4.3）——这恰好是 D1 决策已经提供的路径，也再次印证了选择常驻 MS 的合理性（见 §16.1 Q2）。

**能力探测必须是运行时的，而非文档假设的。** 调研中最危险的例子是 GCS 的 S3 互操作层会**静默忽略**写请求上的条件头——这会让一个"看起来工作正常"的系统在并发下静默破坏线性化。因此 §3.1 的 `ObjectStoreCapabilities` 必须在**连接建立时用真实的冲突写请求实测**，而不是根据厂商文档硬编码。

> ✅ **已实现**（`CapabilityProbe`，`yb-objectstore`）。它在隔离前缀下做 6 项实测：读写、
> 读己之写、`If-None-Match` 条件创建、`If-Match` 比较交换、Range 读、LIST 一致性。
> 任何**关键项**未通过，服务端会**拒绝启动**并说明原因——因为在这种后端上运行
> 会静默损坏数据，而不是仅仅变慢。
>
> 探测的否定用例有专门的测试覆盖（`CapabilityProbeTest` 模拟了「静默忽略条件头」与
> 「弱一致 LIST」两种故障后端）。一个从不失败的探测是没有价值的。

**条件写的错误码语义必须区分**（处理不当会导致重试风暴或静默失败）：

| 错误码 | 含义 | 正确处置 |
|---|---|---|
| `412 PreconditionFailed` | 条件**确定**不成立 | **不要重试**，走冲突处理逻辑 |
| `409 ConditionalRequestConflict` | 并发冲突 | PutObject 可退避重试；**multipart 必须重新 CreateMultipartUpload** |
| `404` | `If-Match` 的目标不存在或是 delete marker | 视为 CAS 目标已消失 |
| `400` | 同一请求同时带两个条件头 | 实现缺陷，不应出现 |

**关于本地文件系统后端**：它存在的唯一目的是让开发和单元测试不需要真实对象存储。必须强制禁止在生产使用——通过一个显式的启动参数（`--i-know-this-is-not-durable`）把关，因为"本地 FS 通过测试但生产环境依赖对象存储语义"是最危险的一类缺陷来源。

### 3.4 对象存储约束与系统级应对

| 约束 | 影响面 | 应对 |
|---|---|---|
| **无原地更新** | 所有写路径 | 不可变对象 + 指针切换（P2）；LSM 天然契合 |
| **每前缀请求速率上限**（S3 约 3500 PUT / 5500 GET 每秒每前缀） | 高并发写入 | 分片前缀天然打散；热点分片内部靠组提交降低 PUT 数（§6.3.4） |
| **Multipart 最小分片 5 MiB** | 追加日志 | 放弃"单对象追加日志"，改用多小对象日志流（D4，§6.3.3） |
| **尾延迟长（p99 可达数百 ms）** | 影响 p99 而非 p50 | 请求对冲（hedged request）：超过 p95 阈值后向另一副本/另一路径发起重复请求，取先返回者 |
| **LIST 是慢操作** | 恢复路径 | 绝不把 LIST 放在热路径；恢复用 `start-after` 增量列举并缓存游标 |
| **不支持事务** | 跨对象原子性 | 单对象 PUT 是原子性的全部；多对象一致性由 manifest 指针保证（先写数据、后换指针、最后删旧） |

## 4. 元数据服务

### 4.1 职责边界

MS 承担四件事，**全部是"短期状态"或"派生状态"**，其权威副本都在对象存储上：

| 职责 | 状态性质 | 丢失后的后果 | 恢复方式 |
|---|---|---|---|
| **TSO** 时间戳分配 | 只需单调递增 | 重启后从快照的 `high_watermark` 继续，跳号即可 | 快照 + 本地预写 |
| **租约** 分片写者仲裁 | 短期（TTL 秒级） | 全部租约过期，写者重新竞选 | 租约本就是易失的，无需恢复 |
| **锁** 行锁/表锁 | 短期（事务期间） | 持锁事务失败回滚 | 无需恢复 |
| **Catalog** 库表元数据与 Schema 版本 | **权威** | 必须能从对象存储完整重建 | 对象存储上的 `catalog/` 是真相源，MS 只是它的缓存与串行化器 |

**关键设计点：Catalog 的真相在对象存储，MS 只是它的写串行化器与读缓存。** 这保证了 MS 完全可丢弃——即使 Raft 日志全丢，也能从 `catalog/` 重建。Raft 的唯一作用是让"并发的 DDL 请求"被串行化到一条确定的序上。

### 4.2 TSO（时间戳分配）

**时间戳格式**：64 位整数，物理部分与逻辑部分分离，便于调试与时间旅行。

```
 63        46 45                    18 17                    0
 ┌───────────┬───────────────────────┬───────────────────────┐
 │ 保留 (18) │  物理时间 ms (28 bit)  │  逻辑计数 (18 bit)     │
 └───────────┴───────────────────────┴───────────────────────┘
```
- 物理部分：Unix 毫秒的低 28 位（约 3.1 天回绕，仅用于时间旅行语义的近似映射；精确的 `AS OF TIMESTAMP` 通过 manifest 中的物理时间字段实现，不依赖此编码）。
- 逻辑部分：同一毫秒内递增，上溢时自旋到下一毫秒。

**两阶段分配（重要，避免可见性歧义）**：

| 事务类型 | 使用的时间戳 | 分配时机 | 是否可预取 |
|---|---|---|---|
| 只读事务 | `start_ts` | 事务开始时 | ✅ 可批量预取 |
| 读写事务 | `start_ts` | 事务开始时 | ✅ 可批量预取 |
| 读写事务 | **`commit_ts`** | **提交决策时实时分配** | ❌ **必须实时** |

`commit_ts` 必须实时分配的原因是：如果批量预取 `commit_ts`，就会出现"预取了 1000、1002 但 1001 对应的事务已放弃"的空洞。此时一个持有 `read_ts=1001` 的读者无法判断该快照是否有效。实时分配保证**已分配的 `commit_ts` 集合在可见性判断上稠密**。

**预取的实现与约束**：
```
CN ──AllocTSO(count=2048, ttl=3s)──▶ MS
                                      │ 返回 [base, base+2048)
                                      │ 记 high_watermark = base+2048
MS ◀── 崩溃重启后从 max(snapshot.hw, 所有未过期预取窗口的右端) 继续
```
预取的 `start_ts` 批次必须带 TTL，且 MS 在恢复时必须把**所有未过期批次的上界**计入水位，否则会出现时间戳回退——这是一个必须写进单元测试的边界条件。

> **实现现状**：批次不是按**个数**而是按**毫秒窗口**申请的（`WindowTso`），
> 因为「多少个时间戳」与「跨 CN 的可见性延迟」之间没有稳定关系，而毫秒窗口有：
> 本 CN 发出去的 `commit_ts` 至多超前另一个 CN 的 `read_ts` 一个窗口。
> 默认窗口是**单 CN 64 秒、多 CN 1 秒**（`--tso-batch-ms`）——上面的
> `count=2048` 读作「一个窗口的额度」即可，数字与取舍见
> [compatibility.md §4.4.2](compatibility.md)。

**降级行为**：MS 不可用时，CN 用剩余预取额度继续服务**只读事务**；写事务阻塞直到 MS 恢复或客户端超时。这个降级语义是刻意的：读是缓存友好的、用户可感知代价小的操作。

### 4.3 租约与 Fencing

写者的选主是系统正确性的核心。规则如下：

```
租约对象（MS 内存 + Raft 副本）：
  Lease { shard, holder_node_id, epoch, expires_at, term }

授予：CN 请求 → MS 检查该分片无有效租约或租约已过期
      → epoch = previous_epoch + 1（单调递增，永不重置）
      → 写入 Raft 日志（保证多数派持久化）
      → 返回 Lease

续租：holder 在 expires_at - renew_margin 前续租；连续续租 epoch 不变

转移：holder 失联超过 TTL → 任意节点可申请 → epoch++ → 新租约
```

**Fencing 的四道防线**（任何一道失效都不能导致数据损坏）：

1. **对象存储写路径**：WAL 对象的 key 中包含 epoch（`wal/e{epoch}/...`）。已罢免写者的 PUT 会落在旧 epoch 前缀下，而 manifest 只引用新 epoch 前缀，旧数据成为孤儿对象被 GC。
2. **Manifest 条件写**：写 manifest 时必须带 `writer_epoch`，且切换 `manifest/CURRENT` 时使用 `If-Match` 校验当前 manifest 的 etag。若已被新写者替换，写入失败。
3. **MS 侧拒绝**：CN 的所有写操作附带 epoch，MS 若发现该 epoch 已被超越，直接拒绝并通知其让位。
4. **读侧校验**：读者在应用 WAL 记录时校验 epoch 与 manifest 中的 `writer_epoch` 一致。

**租约时长的选择**是一个需要在 §16 中评审的取舍：

| 租约 TTL | 故障切换 RTO | 风险 |
|---|---|---|
| 5s | ~5–8s | 网络抖动可能导致误判（假阳性切换），引发写者颠簸 |
| **10–15s（建议默认）** | ~10–20s | 与对象存储的尾延迟量级匹配，误判概率低 |
| 60s | ~60s+ | 故障时写入长时间不可用 |

### 4.4 锁服务

锁的作用范围被刻意收窄——因为**单写者 per 分片已经串行化了同一个分片内的所有写**，锁只需要处理两种情况：

| 场景 | 机制 |
|---|---|
| 同分片内的写写冲突 | **不需要锁**，单写者队列天然串行（这是单写者模型的核心收益） |
| 跨分片事务的提交冲突 | **不需要锁**，用 2PC 的 primary record 判定（§7.3） |
| **跨分片写同一行**（如两个事务分别更新同一账户的不同分片副本） | 需要：MS 上的**行锁表**（key = `table#pk` 的哈希），带 TTL 防泄漏 |
| DDL 与 DML 的冲突 | MS 上的**表级意向锁**（`SHARED`/`EXCLUSIVE`） |
| `SELECT ... FOR UPDATE` | 同上行锁表，语义与 MySQL 对齐 |
| 唯一约束冲突检测 | 索引上的**唯一性锁**，或用一个"唯一性校验 + 悲观插入"的短程锁 |

锁表在 MS 内存中实现（一个 `ConcurrentHashMap<LockKey, LockEntry>`），**不持久化**——MS 重启意味着所有持锁事务失败，这是可接受的（事务会重试）。锁等待超时与死锁检测采用 MySQL 语义的 `innodb_lock_wait_timeout`（默认 50s），死锁检测用简单的等待图环检测。

### 4.5 Catalog

Catalog 是库、表、列、索引、分区、用户与权限的元数据。**真相源是对象存储上的 `catalog/` 目录**，采用与数据面相同的"不可变版本 + 指针"模式：

```
catalog/
  db/{db_id}.json                  # 库定义（可变，小对象，频率低）
  table/{table_id}/
    schema.{version}.json          # 不可变；每次 DDL 生成新版本
    CURRENT                        # 指针 → 当前 schema version
  table/{table_id}/indexes.json    # 索引定义集合（附版本）
  users.json                       # 用户与授权（可变）
```

CN 侧的 Catalog 缓存：一个 `ConcurrentHashMap<TableId, CachedSchema>`，用 `CURRENT` 对象的 etag 做失效判定。DDL 提交后，MS 通过 gRPC 广播通知所有在线 CN 主动失效（失败时退化为周期轮询，周期 5s）。

**Schema 版本与在线 DDL 的配合**：每个数据文件与索引段都记录其构建时的 `schema_version`。读时如果 `file.schema_version < table.current_schema_version`，用**schema 演化规则**（加列给默认值、删列忽略、类型放宽）在读取时做投影，而不是重写数据。这样 `ALTER TABLE ADD COLUMN` 是**纯元数据操作，O(1) 且不阻塞**——这是对象存储不可变模型的一个自然红利。

### 4.6 持久化与恢复

MS 的 Raft 日志与快照落在对象存储上：

```
meta/ms/
  snapshot/{term}-{index}.snap    # 状态机快照（TSO 水位、Catalog 版本、用户表）
  log/{term}/{index:012d}.log     # Raft 日志段（批量攒批后上传）
  CURRENT                         # 指针 → 最新 snapshot + 起始 log index
```

由于 Raft 日志的写入频率远低于数据面（TSO 分配在内存中完成，只有**水位推进**、**租约授予**、**DDL** 才落日志），这里可以安全地采用较大的攒批窗口（如 100ms），把 PUT 数压到很低。

**冷启动时长**目标：`< 3s`（加载最新快照 + 重放少量日志）。这是选择"状态落对象存储"而非"落本地盘"的代价——启动慢一点，但换来 MS 节点可以随时被抢占/迁移。

### 4.7 双模式部署（Q2 已决策）

> **本节描述的是一个一等的部署选项，不是降级预案。**
> **Q2 的决定是「双模式，部署时选择」**——两种实现都要交付，由部署者按成本/延迟取舍。

架构上**不依赖** MS 的存在。把协调职责抽象为接口后，提供两个可互换的实现：

```kotlin
interface CoordinationService {
    suspend fun allocTimestamp(count: Int, ttl: Duration): TimestampBatch
    suspend fun acquireLease(shard: ShardId, ttl: Duration): Lease?
    suspend fun tryLock(key: LockKey, ttl: Duration): LockHandle?
    fun watchCatalog(tableId: TableId, onChange: (SchemaVersion) -> Unit)
}
```
| 实现 | 机制 | 交付 | 适用 |
|---|---|---|---|
| **`SingleProcessCoordination`** | 进程内：时间戳走对象存储水位，租约与锁由**部署方式**保证（只有一个 CN） | 已交付（本节下方的「实现现状」） | **单 CN 部署，出厂的 `--coord-mode` 默认值** |
| **`MetaServiceClient`** | 到 3 节点 MS 的 RPC（**实现是手写的长度前缀 JSON，不是 gRPC**） | **M1** | 追求低延迟；能接受 3 台小规格常驻实例的成本 |
| **`ObjectStoreCoordination`** | 用 `If-None-Match` / `If-Match` 在对象存储上做 CAS 选举与粗粒度授时 | **M1**（与上一个同批交付） | **零常驻成本**；可接受每次提交多 1–2 个 RTT |

> **实现现状**：三种模式都已交付，由 `--coord-mode` 选择（`single` / `objectstore` / `ms`），
> **默认 `single`**——单 CN 下既不需要常驻 MS，也不需要每次提交多付 1–2 个 RTT。
> `--role ms` 可让一个进程只跑元数据服务，`--run-meta-service` 让 CN 进程内顺带跑一个 MS 节点。
> 三种模式共用**同一套一致性测试**。数字与部署取舍见
> [compatibility.md §4.4.2](compatibility.md)、`:yb-bench:benchCoordination`。

**两种模式的取舍**：

| 维度 | 常驻 MS | 纯对象存储 |
|---|---|---|
| 常驻实例成本 | 3 台小规格（§13 量化为 ¥0–180/月） | **0** |
| 提交延迟 | 基线 | +1–2 × RTT |
| 租约边界情况的测试难度 | 中 | **高**（CAS 选举的边界情况极难穷尽） |
| 依赖的前提 | 无 | 后端必须支持条件写（`conditionalCreate`，§3.3） |

**两个必须遵守的实现约束**：

1. **接口从第一天就按 `CoordinationService` 抽象写**，禁止在任何业务代码中出现 `MetaServiceClient` 的具体类型。否则后期无法回收（这正是 Q2 选择"双模式"而非"只做常驻 MS"的代价，也是它的价值）。
2. **`ObjectStoreCoordination` 在不支持条件写的后端上必须启动即失败**，而不是静默退化——`conditionalCreate == false` 时它是无法正确工作的（§3.3 的降级路径假设的是 MS 存在）。

**测试要求**：由于纯对象存储模式的租约边界情况极难穷尽，**两种模式必须共用同一套并发/故障注入测试**（`yb-testkit` 中把 `CoordinationService` 作为可替换的实现注入）。这是 Q2 决策带来的额外测试成本，必须在 M1 的验收中包含。

### 5.2 键设计的三条规则

**规则 1：前缀承载分片，负载打散在后缀。**

```
前 16 字节决定对象存储的内部分区（S3 按前缀的哈希分区）：
  shard/{table_id}/{partition_id}/...        ← 同分片的对象天然相邻，LIST 高效
后缀 file_id / seq 用零填充定长数字或高熵 ID   ← 同前缀内的请求均匀分布
```
给定时，**同一分片的对象聚集在一个前缀下**，这让 LIST 与 GC 高效；而分片本身数量多，天然把请求分散到不同前缀。分片是"天然的分区键"。

**规则 2：热对象与冷对象物理分离。**

这是 §2.3 那条"1 次 GET"路径的实现基础：

| 对象 | 典型大小 | 访问模式 | 缓存策略 |
|---|---|---|---|
| `manifest/CURRENT` | < 1 KB | 每次查询都可能读 | 内存常驻 + 条件 GET 校验 |
| `M-*.mf` | 10 KB – 2 MB | 随 CURRENT 变更 | 内存常驻 |
| `f_*.idx` | 1–5% 的数据大小 | 每次点查/范围查 | **内存常驻**（容量允许时） |
| `f_*.dat` | 8–64 MB | 按字节范围读 | LRU + 本地 NVMe 二级缓存 |
| `wal/e*/**.log` | 100 KB – 8 MB | 只在追赶/恢复时读 | 短 TTL，不常驻 |

如果 `.idx` 与 `.dat` 合并成单个对象，点查就必须下载整个 8–64 MB 的对象——**这会直接摧毁本设计的性能前提**。分离是强制的（决策 D6）。

**规则 3：版本号单调递增，永不复用。**

`seq`、`file_id`、`segment_id`、`epoch`、`schema_version` 全部只增不减。这让缓存失效判定退化为一次整数比较，也让"读到一个旧版本"永远安全。

### 5.3 对象命名规范

```kotlin
object ObjectKeys {
    fun manifestCurrent(t: TableId, p: PartitionId) = "shard/$t/$p/manifest/CURRENT"
    fun manifestSnapshot(t: TableId, p: PartitionId, seq: Long) =
        "shard/$t/$p/manifest/M-${seq.pad12()}.mf"

    /** epoch 在路径中，是 fencing 的第一道防线 */
    fun walBatch(t: TableId, p: PartitionId, epoch: Long, seq: Long) =
        "shard/$t/$p/wal/e$epoch/${seq.pad12()}.log"

    /** file_id 采用 时间有序 + 随机 的混合 ID，避免同前缀热点 */
    fun sstData(t: TableId, p: PartitionId, lvl: Int, fid: FileId) =
        "shard/$t/$p/sst/L$lvl/${fid}.dat"
    fun sstIndex(t: TableId, p: PartitionId, lvl: Int, fid: FileId) =
        "shard/$t/$p/sst/L$lvl/${fid}.idx"
}

/** ULID 风格：48 位时间戳 + 80 位随机，字典序即时间序 */
@JvmInline value class FileId(val value: String)
```

**零填充定长数字**（`pad12()`）是必需的：对象存储的 LIST 是**按字节字典序**的，`10.log` 会排在 `9.log` 之前。这是一个廉价的、但一旦漏掉就会导致恢复时日志乱序的严重缺陷。

### 5.4 请求数预算

按原则 P4，把每个操作的请求数显式列出，作为实现时的验收基准：

| 操作 | 冷缓存 | 稳态（缓存热） | 说明 |
|---|---|---|---|
| 点查 | 3 GET（`.idx` + `.dat` 范围 + manifest 校验） | **1 GET** | 见 §2.3 |
| 索引点查 | 4–5 GET | **1–2 GET** | 多一跳索引 → 主键 |
| 范围扫描（1000 行） | 2 + ⌈range/block⌉ GET | 同左（顺序预取） | 前缀扫描几乎不可缓存 |
| 小事务提交（组提交，批 50） | **1 PUT**（摊薄后 0.02/事务） | 同左 | 见 §6.3.4 |
| 读事务开始 | 0（预取 TSO） | 0 | — |
| 全文检索（top-100） | 1 + 段数 + 命中块数 | 3–8 GET | 见 §8.6.6 |

**这个表应当被实现为运行时可观测指标**（`yb_objectstore_requests_total{op, cached}`），并在 CI 里做回归门禁——请求数一旦退化，成本会立刻在账单上体现出来。

## 6. 存储引擎

### 6.1 总体结构

存储引擎是教科书式的 LSM，但每一层都为"对象存储"这个物理前提做了改造。**与本地 LSM（RocksDB 等）的关键差异**用 ★ 标出：

```
        写路径                                读路径
   ┌──────────────┐                     ┌──────────────────────┐
   │  事务写缓冲   │                     │   read_ts 快照        │
   └──────┬───────┘                     └──────────┬───────────┘
          ▼                                        ▼
   ┌──────────────┐   ★ 攒批      ┌──────────────────────────────┐
   │  Group Commit │──────────────▶│ MemTable (内存跳表, 可变)      │
   │  攒批器       │               └──────────┬───────────────────┘
   └──────────────┘                          │
          │ 一个批次 = 一个对象                 ├──▶ L0 文件（bloom 筛选）
          ▼                                   ├──▶ L1 文件
   ┌──────────────┐   ★ 每次 PUT        ├──▶ L2 ...
   │  WAL 对象流  │   都是新建对象      └──▶ 逐层合并（MVCC 可见性过滤）
   └──────┬───────┘
          │
          ▼
   ┌──────────────┐   ★ 索引块与数据块
   │  MemTable    │──── 分离成两个对象 ────▶ f_xxx.idx (热) + f_xxx.dat (冷)
   │  flush       │
   └──────┬───────┘
          ▼
   ┌──────────────┐   ★ 在对象存储上做
   │  Compaction  │      受流量成本约束
   └──────────────┘
```

### 6.2 MemTable

内存中的有序表，按 `(user_key, commit_ts DESC)` 排序——`commit_ts` 降序排列让同一 `user_key` 的最新版本排在最前，读时取第一个可见版本即可短路。

```kotlin
/**
 * key = user_key || ~commit_ts (8B 大端取反)
 * 取反使得同一 user_key 下 commit_ts 越大的版本排序越靠前。
 */
class MemTable(private val capacityBytes: Long) {
    private val table = ConcurrentSkipListMap<ByteArrayKey, RowValue>(ByteArrayKey.COMPARATOR)
    private val used = AtomicLong(0)

    fun put(key: ByteArray, ts: CommitTs, value: ByteArray?)  // null = 墓碑
    fun get(key: ByteArray, readTs: ReadTs): RowValue?
    fun scan(from: ByteArray, to: ByteArray, readTs: ReadTs): Iterator<RowValue>
    fun freeze(): ImmutableMemTable
}
```

**关键差异（对比 RocksDB）**：MemTable **不需要**在每次写入后等待 WAL 落盘。它先进入 MemTable，由 Group Commit 攒批器异步决定何时批量持久化（§6.3.4）。这是延迟优化，代价由提交延迟策略显式承担。

### 6.3 WAL：对象存储上的写前日志

#### 6.3.1 为什么不能用单对象追加

最自然的想法是"打开一个 `wal.log`，不断追加"。这在对象存储上**不可行**：

- S3 的 PUT 全量覆盖对象，没有 append 语义；
- Multipart Upload 提供了近似的追加能力（逐个 `UploadPart`，最后 `CompleteMultipartUpload`），但**除最后一片外，其余分片必须 ≥ 5 MiB**（S3 硬性约束）。在低延迟场景下等 5 MiB 数据才持久化一次，等价于放弃了事务的持久性承诺。

> **一个值得跟踪的例外：S3 Express One Zone 支持 append**（2024-11 GA）。它通过 `x-amz-write-offset-bytes` 头向对象追加，**单次追加 ≤ 5 GB、单对象 ≤ 10,000 parts**，没有普通 Multipart 的 5 MiB 最小分片限制。这理论上允许"单个可追加的 WAL 对象"这一更优雅的形态。
>
> **但本项目暂不采用它**，原因有三：(1) 它只在 Express One Zone 可用，而该层**不支持 `PutObject` 条件写**（§3.3.1）；(2) 单对象 10,000 parts 的硬上限意味着仍需分段轮转，复杂度并未真正降低；(3) 该 API 的 ETag **不是 MD5**，无法复用现有的完整性校验路径。
>
> **记为 M5 的评估项**：如果实测显示它能把 WAL 的请求数再降一个数量级，值得重新评估。

因此采用 **D4：多小对象日志流**。

#### 6.3.2 日志流的结构

```
wal/e42/
  0000000100.log   ← 一个组提交批次，包含 30 个事务
  0000000101.log   ← 下一个批次
  0000000102.log
  ...
  s-0000000100-0000000131.log   ← 后台合并产物：把小对象合并成 8 MiB 的段
```

- **写**：每次组提交产出一个新对象，键为单调递增的 `seq`。
- **读/恢复**：`GET manifest/CURRENT` 得到 `wal.effective_from_seq`，然后 `LIST wal/e42/` 并 `start-after` 增量列举，按键序（= 时间序）逐个读取。
- **合并**：当日志对象数超过阈值（如 128 个）时，一个后台任务把它们读出来合并成一个 8 MiB 的段对象，并更新 manifest 的 `wal.effective_from`。这让恢复时的 LIST + GET 次数保持在个位数。

#### 6.3.3 日志对象的格式

```kotlin
/**
 * WAL 对象磁盘格式（所有整数小端序）
 *
 *  ┌─────────────────────────────────────────┐
 *  │ Header (64 B)                            │
 *  │   magic:        "YBWL"       (4 B)       │
 *  │   format_ver:   u16          (2 B)       │
 *  │   epoch:        u64          (8 B)  ← fencing 校验
 *  │   seq:          u64          (8 B)       │
 *  │   batch_count:  u32          (4 B)       │
 *  │   min_commit_ts:u64          (8 B)       │
 *  │   max_commit_ts:u64          (8 B)       │
 *  │   payload_len:  u32          (4 B)       │
 *  │   header_crc:   crc32c       (4 B)       │
 *  │   reserved:                  (22 B)      │
 *  ├─────────────────────────────────────────┤
 *  │ Payload: 串接的 BatchRecord               │
 *  │   BatchRecord { tx_id, commit_ts,        │
 *  │                 ops: [Put|Delete],       │
 *  │                 record_crc }             │
 *  ├─────────────────────────────────────────┤
 *  │ Footer (8 B): total_crc32c + magic       │
 *  └─────────────────────────────────────────┘
 */
```
**每个 BatchRecord 带独立 CRC**，而不是只校验整体——这样一个字节的损坏只影响一个事务，而不是整批 30 个事务。读取时跳过坏的记录并记录告警，而不是让整个分片不可用。

#### 6.3.4 组提交（Group Commit）：延迟与成本的调节阀

这是写路径上**最重要的一个旋钮**，直接决定提交延迟与请求费用的乘积。

```
时间 ──────────────────────────────────────────────────────▶

提交请求到达:  T0   T0+1  T0+2  T0+3 ...  T0+9
                │    │     │     │         │
                └────┴─────┴─────┴─────────┘
                          │
                    [攒批窗口 10ms]
                          │
                          ▼
                   单次 PUT (对象 0000000100.log)
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
        ACK 全部 10 个事务     写者继续处理下一批
       (延迟 ≈ 10ms + RTT)
```

**三档提交模式**（可按表/会话配置）：

| 档位 | 攒批窗口 | 提交延迟 p50 | 每次 PUT 摊薄的事务数 | 适用 |
|---|---|---|---|---|
| `sync`（**出厂默认**，Q1 决策） | min(5ms, 等满 256KB) | ~30–50ms | 1–50 | 常规业务，**RPO=0** |
| `batch` | min(50ms, 等满 4MB) | ~100–150ms | 50–2000 | 高吞吐导入，可容忍延迟 |
| `async`（**需显式声明**，Q1 决策） | 100ms，不等待 PUT 完成就 ACK | **< 1ms** | 50–2000 | 日志/埋点类，**RPO > 0**（崩溃丢失 ≤100ms 数据） |

**`async` 档必须显式声明，且出厂默认值永远是 `sync`**（Q1 决策）。这条约束的理由是：`async` 的代价是 **RPO > 0**，即崩溃时丢失最多 100ms **已经 ACK 给客户端**的写入。对一个事务型数据库而言，把"已确认的写入可能丢失"设为默认行为是不可接受的——即使用户只是"忘了改配置"，责任也在系统而非用户。因此：

- 出厂默认 `sync`（RPO=0）；
- `async` 需在**表级或会话级显式声明**；
- 无论在哪个层级开启，`SHOW VARIABLES LIKE 'commit_mode'` 都必须**如实返回**，并在连接建立时的会话信息中可见——**让使用者明确知道自己放弃了什么**，而不是把它藏起来。

**如果日后确实需要"整个部署默认 async"**（例如一个纯日志采集的实例），通过部署级配置实现而不是改变出厂默认，并保持优先级链：`会话 > 表 > 部署默认 > 出厂`。

**攒批窗口的自适应**：窗口不是固定的，而是按近期到达率动态调整——空闲时窗口趋近于 0（写入立即触发 PUT，因为此时请求数少，成本不敏感且延迟最重要）；高负载时窗口扩大到上限（此时成本敏感且单事务延迟已被排队稀释）。这个自适应用一条简单的规则实现：**窗口 = clamp(目标PUT间隔 / 观测到的到达率, 0, maxWindow)**。

### 6.4 SST 文件格式：索引与数据分离

这是 D6 决策的具体化，也是 §2.3"1 次 GET 点查"的实现载体。

**两个对象：**

```
f_01H8XQ....dat  (64 MiB)              f_01H8XQ....idx  (~800 KB)
┌──────────────────────┐               ┌───────────────────────────────┐
│ Data Block 0  (64KB) │◀── 范围读 ──  │ Header: min_key, max_key,      │
│ Data Block 1  (64KB) │               │         row_count, schema_ver, │
│ ...                  │               │         commit_ts_range        │
│ Data Block N  (64KB) │               │ BlockIndex[]:                  │
│                      │               │   { offset, length,           │
│                      │               │     first_key (前缀压缩),      │
│                      │               │     min_commit_ts,            │
│                      │               │     max_commit_ts,            │
│                      │               │     row_count,                │
│                      │               │     col_stats: 每列 min/max/  │
│                      │               │                null_count }   │
│                      │               │ BloomFilter (10 bits/key)     │
│                      │               │ SuffixArray/Trie (可选，前缀)  │
│                      │               │ Footer: crc32c                │
└──────────────────────┘               └───────────────────────────────┘
   冷：按字节范围取 4–64 KB                 热：整体常驻内存
```

**`.idx` 对象的内部布局**（按访问频度从高到低排列，让缓存可部分加载）：

| 区段 | 占比 | 用途 |
|---|---|---|
| BlockIndex[] | ~70% | 数据块的偏移、首 key、行数、commit_ts 范围 |
| **列级 min/max 统计** | ~15% | **跳数索引的载体**——谓词下推时直接在内存中剪掉整块 |
| BloomFilter | ~12% | 点查判定"key 是否可能在本文件" |
| Header/Footer | 极小 | — |

**为什么列统计放在 `.idx` 里是划算的**：它让"`WHERE age > 60` 的查询可以跳过 95% 的数据块"这个判断**完全在内存中完成，零 IO**。这是对象存储上最重要的优化模式——**用元数据的计算替代数据的读取**。§8.5 的跳数索引就是把这个思路系统化。

**数据块内的行格式**：行式存储 + 前缀压缩的 key + 按 schema 顺序的值（变长编码），块内可选做 LZ4 压缩（默认开启，`compress=false` 可关）。块级压缩而非文件级压缩是必需的——文件级压缩会让范围读失效。

### 6.5 Manifest

Manifest 是分片的"根指针"。设计上要为两个矛盾的目标服务：**读取要快**（每次查询都要用）和**更新要便宜**（每次 flush/compaction 都产生）。

**两级结构**：

```
manifest/CURRENT          (指针, <200 B, 唯一可变的根)
    │ 内容: { seq: 100234, snapshot: "M-0000100234.mf",
    │         deltas: ["d-0000100235.mf", ...], etag: "..." }
    ▼
manifest/M-0000100234.mf  (全量快照, 每次超过 N 个增量时重写)
    │  内容: 所有 L1+ 层的文件清单（L1+ 是 sorted run，数量少）
    ▼
manifest/d-0000100235.mf  (增量, 只记录 L0 的变化, 数百字节)
```

**为什么这样分层**：L1+ 层是**有序运行（sorted runs）**，文件数少且稳定，适合放在全量快照里；L0 是频繁产生的、无序的、文件多的层——它每次 flush 都变化，用增量记录。读取时 `CURRENT + deltas` 在内存中合并成一个视图。

**Manifest 读取的缓存策略**（这是 §2.3 路径里的第 ② 步）：

```kotlin
class ManifestCache(private val store: ObjectStore, private val clock: Clock) {
    private val cache = AtomicReference<ManifestView>()
    private val lastCheck = AtomicLong(0)

    /**
     * 稳态下每次调用只发生一次 304 校验（零字节传输），
     * 且该校验被限频到 checkInterval（默认 200ms）。
     * 写者自己的写入会直接更新本地视图，不经网络。
     */
    suspend fun view(shard: ShardId): ManifestView {
        val now = clock.millis()
        val cached = cache.get()
        if (cached != null && now - lastCheck.get() < checkIntervalMs && !writerIsLocal(cached)) {
            return cached
        }
        val etag = store.head(ObjectKeys.manifestCurrent(shard)).etag
        if (cached?.etag == etag) { lastCheck.set(now); return cached }   // 304 路径
        return refresh(shard).also { cache.set(it); lastCheck.set(now) }
    }
}
```

这里有一个必须显式声明的**语义取舍**：README 级别的快照隔离要求读者看到一个一致的 `read_ts` 快照。而 manifest 的限频刷新意味着读者的**物理文件视图可能落后于其 `read_ts`**。这是安全的，因为：

- manifest 只增不减地添加文件。旧 manifest 视图是当前视图的**子集**（在 GC 水位之上）；
- 一个 `read_ts` 为 T 的读事务，只需要读取"包含 `commit_ts ≤ T` 的版本"的文件。落后于最新 manifest 只是可能**读不到刚提交的数据**——而这恰恰是它应有的行为；
- 唯一的危险是 **GC 已经删除了它需要的旧文件**。因此 GC 水位（§6.9）必须保守：**GC 只删除 `commit_ts_watermark < 最老的活跃 read_ts - 安全边界` 的文件**，而最老的活跃 `read_ts` 由 MS 维护。

这条推理链是整个系统正确性的关键，**必须有一个专门的并发测试来覆盖**：一个长时间运行的读事务与 GC、compaction 并发执行，验证读事务不丢行、不报错。

### 6.6 Compaction

LSM 在对象存储上的 compaction 与本地有本质不同：**读-改-写产生的流量和请求是要花钱的**，而本地盘上是"免费的"（只是 CPU 与 IO 时间）。因此策略必须显式地用成本来约束。

**分层策略：**

| 层 | 类型 | 目标大小 | 触发条件 | 策略 |
|---|---|---|---|---|
| L0 | 无序 | 64 MiB | 文件数 ≥ 4 | 与 L1 中有重叠的文件合并 |
| L1 | **leveled（层内不重叠）** | 512 MiB | 超过阈值 | 选一个 L1 文件与重叠 L2 文件合并 |
| L2 | **leveled** | 4 GiB | 同上 | 逐个合并 |
| L2+ | **leveled** | — | 冷数据 | **下沉到低频存储层**（§13.3） |

> **⚠️ 硬约束：L1 及以下必须是 leveled，不能使用 tiered/universal。**
>
> 这不是性能偏好，而是 **§8.9 的 COUNT 优化依赖的语义前提**——"key 在 L1+ 中至多出现一次"才使 `Σ file.row_count` 无重复。
> 若日后为降低写放大想改用 tiered 布局，**必须先解决 §8.9.3 的重复计数问题**，否则 `SELECT COUNT(*)` 会静默返回错误结果。

**对象存储专属的三个优化：**

1. ~~**Compose 免流量拼接**~~：**已评估，当前不做**（理由见 §3.2 的决策记录：两层布局下
   不存在可原样保留的区间；S3 的 5 MiB 最小片长让 KB 级对象的服务端拼接根本走不到，
   兜底路径反而多花请求）。触发重新评估的条件也记在那里。
2. **空 compaction 探测**：合并前先用所有输入的 `.idx` 判断是否存在重叠以及重叠比例。如果输出的 90% 与单个输入相同（常见于 append-only 工作负载），则**跳过本次 compaction**——收益低而成本高。这个"**compaction 收益预估**"是对象存储场景下必需的，本地 LSM 通常不做。
3. **限速与窗口**：compaction 是带宽密集型任务。它必须受一个**全局带宽预算**约束（默认：不超过对象存储配额的 50%），并能被配置为只在低峰时段运行。

**Compaction 的后台执行位置**：由分片的**当前写者**兼做（它已经持有租约）。这不是可选的——只有写者才能安全地切换 manifest 指针。但引入一个**辅助角色**：任意 CN 可以注册为 compaction worker，从 MS 领取"计算合并计划"（读取输入、生成新文件），最后由写者做提交。这让 compaction 的 CPU/带宽开销可以分摊到多台机器上。首版可以先让写者独占，作为优化项记录。

### 6.7 缓存体系

三层次，全部是**可丢弃的**（P1）：

```
 ┌────────────────────────────────────────────────┐
 │ L1: 内存 Block Cache (Caffeine, 按权重 LRU)      │
 │     ~ 堆内存的 60%; 权重 = 对象字节数             │
 │     优先级: .idx 对象 > manifest > 热数据块       │
 ├────────────────────────────────────────────────┤
 │ L2: 本地 NVMe Disk Cache (RocksDB/Speedb 实例)   │
 │     key = object_key#etag, value = 对象字节       │
 │     ★ 不可变对象 → 缓存永不失效，只需淘汰          │
 │     容量: 磁盘的 80%                             │
 ├────────────────────────────────────────────────┤
 │ L3: 元数据常驻区 (独立预算, 不受 LRU 影响)         │
 │     所有已打开分片的 manifest / CURRENT           │
 │     已加载文件的 .idx 摘要 (BlockIndex + 列统计)  │
 │     ★ 这部分永不淘汰 —— 它是 "1 次 GET" 的保证     │
 └────────────────────────────────────────────────┘
```

**L2 缓存的一个关键性质**：因为所有数据对象都是不可变的，`(object_key, etag)` 唯一确定内容，**缓存条目永远不会过期或失效**——只需要按容量淘汰。这比传统数据库的 buffer pool 简单得多，也可靠得多（不存在"脏页"概念）。RocksDB 在这里被当作一个**纯 KV 的本地缓存**使用，它的 WAL、事务、compaction 全部关闭。

**L3 常驻区的容量约束**（必须核算，否则会 OOM）：

```
常驻内存 ≈ Σ_已打开分片 ( manifest 视图 + Σ_文件 ( .idx 的 BlockIndex 与列统计部分 ) )

单个文件的常驻开销 ≈ 每 64 KiB 数据块 × ( ~64 B BlockIndex + 列数 × ~16 B 列统计 )
                    = 每 64 KiB 数据 → 约 64 B + 列数×16 B
按 10 列计算: 每 MiB 数据 → 约 3.5 KB 常驻内存
故: 1 TiB 数据 → 约 3.5 GiB 常驻内存

这在小规模场景（≤100 GiB）只需 ~350 MiB，完全可接受。
超出时按分片 LRU 淘汰整个常驻区（而非逐文件），避免碎片化。
```

#### 6.7.1 并发读去重（Request Coalescing）—— 必须实现，不是可选优化

**这是缓存体系里最容易被漏掉、但代价最大的一环。**

场景：一个热点对象（比如某个分区的 `manifest/CURRENT`，或一个被频繁访问的 `.idx`）缓存未命中，此时有 50 个并发查询同时需要它。

```
没有去重：         50 个协程 → 50 次对象存储 GET（同样的 key）→ 50 倍请求费用 + 50 倍带宽
有去重（本设计）：  50 个协程 → 1 次 GET，其余 49 个 await 同一个 Deferred
```

实现：在缓存层维护一个 `ConcurrentHashMap<ObjectKey, Deferred<ObjectData>>` 作为"在途请求表"，第一个发起者的 `Deferred` 被后来者共享，完成后移除。

```kotlin
class CoalescingLoader(private val store: ObjectStore) {
    private val inFlight = ConcurrentHashMap<ObjectKey, Deferred<ObjectData>>()

    suspend fun load(key: ObjectKey, range: ByteRange?): ObjectData {
        val existing = inFlight[key]
        if (existing != null) return existing.await()          // ★ 复用在途请求
        val deferred = scope.async(start = CoroutineStart.LAZY) {
            try { store.get(key, range) } finally { inFlight.remove(key) }
        }
        val prev = inFlight.putIfAbsent(key, deferred)
        if (prev != null) return prev.await()                  // 竞争失败，用别人的
        deferred.start()
        return deferred.await()
    }
}
```

**为什么在这个系统里格外重要**：缓存未命中往往具有**时间聚集性**（同一时刻大量查询需要同一批刚被 compaction 替换的 `.idx`）。如果没有去重，一次 compaction 就可能引发一次请求风暴。参考实现：Chroma 的 `AdmissionControlledS3Storage` 同时做了这件事与优先级队列（P0/P1）。

**去重要与淘汰协同**：新加载的对象进入缓存时，可能触发 LRU 淘汰出刚被另一个协程持有的对象。需要保证"被引用的对象不被淘汰"（引用计数或"淘汰后延迟释放"）。

#### 6.7.2 缓存预热提示

对象存储数据库的冷启动代价极高（§14.1：冷热比约 60 倍）。因此必须提供**主动预热**能力，而不是等待流量把缓存"焐热"：

| 机制 | 说明 |
|---|---|
| **`yb-cli warm --table=orders --partition=p3`** | 读取指定分片的所有 `.idx` 对象与 manifest，填入 L2/L3 |
| **分区 pinning** | 标记某表/分区为"常驻"，其元数据区不被 LRU 淘汰（§6.7 L3 已默认如此） |
| **应用侧提示** | `SELECT /*+ WARM(partition) */ ...` 或会话变量，供应用在预知流量前调用 |
| **预测性预热** | 记录"某查询模式上次读了哪些对象"，在相同模式再次出现时提前加载 |
| **CN 变更时的交接** | CN 优雅关闭前，把其缓存索引清单写入 `ops/cachewarmer/{node_id}.json`，新 CN 可据此优先加载最高频的元数据（⚠️ 仅传清单，**不传数据**——否则违反 P1 无状态原则） |

**必须守住的原则**：预热只允许填充**元数据与索引对象**（`.idx`、manifest），不允许把数据块也预热——否则等于把"缓存"变成了"必须搬迁的状态"，破坏 P1。

### 6.8 崩溃恢复

CN 是无状态的，所以"崩溃恢复"实际上是**新写者接管分片**的流程：

```
1. 新写者 cn-7 从 MS 获得租约 (epoch: 42 → 43)
2. 读取 manifest/CURRENT，得到 { snapshot, deltas, wal.effective_from }
3. LIST wal/e43/ ... 实际为空；读取 wal/e42/ 中 > effective_from 的日志对象
4. 逐个读取并重放到 MemTable（校验 epoch，跳过损坏记录并告警）
5. 生成一个新的 L0 SST（.idx + .dat），写入 sst/L0/
6. 写入新 manifest：writer_epoch=43, wal.effective_from=<e43 的第一个 seq>
   → 用 If-Match 校验 CURRENT 的 etag，若失败说明有更新的写者，放弃
7. 更新 CURRENT 指针（原子）
8. 开始接受写入
```

**恢复时间估算**：假设日志积压 64 MiB（未 flush 的数据），恢复需要在 1 个 RTT 内完成读取 + 1 次写入 fsync + manifest 切换。

```
恢复耗时 ≈ LIST(200ms) + GET 64MiB 日志(并行 8 流, ~1s)
           + flush 生成 SST + PUT .dat/.idx (~2s) + manifest 切换(~100ms)
         ≈ 3–5 秒
```

**这个估算决定了租约 TTL 必须显著大于恢复时间**（10–15s > 5s），否则会出现"新写者还在恢复，租约又过期了"的活锁。这是 §4.3 中 TTL 建议值的量化依据。

**恢复的确定性**要求：重建的 SST 必须**内容确定**（同样的输入产生同样的输出），否则不同节点接管会产生不同的文件，导致 cache 与备份不一致。这通过固定排序与固定块边界实现。

### 6.9 垃圾回收

对象存储没有"删除即释放"的强一致保证（删除一个对象后，已缓存的读可能仍能读到）。因此 GC 采用保守的**两阶段延迟删除**：

```
阶段 1（标记）：从当前 manifest 出发，计算所有可达对象集合 R
                 LIST 前缀下的所有对象集合 A
                 待删 = A - R，且 对象的 created_at < now - 安全窗口(默认 24h)
                 写入 ops/garbage/{ts}/{uuid}.json

阶段 2（删除）：延迟 24h 后，按清单逐个删除，删除后记录到 audit
                删除失败的对象留给下一轮
```

**24 小时安全窗口的依据**：任何长于 24 小时的读事务都是异常情况（且应被 `max_statement_time` 之类限制拦截）。窗口可配置，但缩短它会显著提高"读者正好在读一个已被删除的文件"的概率。

**孤儿对象的主要来源**（需要在监控中区分，它们是不同的 bug）：
1. Compaction 产生的、未被任何 manifest 引用的中间文件（正常）；
2. 被 fence 掉的旧写者留下的 WAL 对象（**正常且预期**，见 §4.3）；
3. 上传中断留下的 multipart 残留（**需要专门的清理**，S3 有 Lifecycle 规则可自动处理）；
4. 真正的泄漏（**是 bug**，需要告警）。

## 7. 事务

### 7.1 MVCC 与可见性

每个行版本携带 `commit_ts`。读事务在开始时取得 `read_ts`，可见性规则为：

```
行版本 V 对 read_ts = T 可见  ⟺  V.commit_ts ≤ T 且 V 未被删除墓碑覆盖

删除表达为写入一个 value=null 的墓碑版本（tombstone），commit_ts 为删除事务的提交时间。
```

**为什么用 `commit_ts` 而不是 `start_ts` 排序**：用 `commit_ts` 排序使"提交顺序"成为唯一的可见性序，避免了"一个长事务的 start_ts 很早但提交很晚，导致后来的事务看不到它但更早的读却能看到它"这类异常。这与 Percolator / TiKV 的模型一致。

**GC 水位**：`gc_watermark = min(所有活跃事务的 read_ts) - 安全边界`。低于该水位的旧版本可以在 compaction 时物理丢弃。水位由 MS 维护（它知道所有活跃事务），周期性写入 `tx/gc_watermark.json`。

（一个需要评审的细节：如何在 CN 崩溃时正确回收其持有的 `read_ts`，避免水位被一个死掉的事务永久压住。方案是在 MS 中给每个 `read_ts` 注册一个 TTL 租约，CN 需定期续约；崩溃后 TTL 到期即视为事务已死。）

### 7.2 单分片事务：无锁串行

因为每个分片只有一个写者（租约持有者），**同一分片内的所有写事务在逻辑上被串行化在写者的一个队列里**。这带来三个重要收益：

1. 不需要行锁来做同分片写冲突检测；
2. 不需要冲突检测与重试（写不会失败，只会排队）；
3. WAL 的追加天然是有序的，恢复简单。

写者的处理循环：

```kotlin
class ShardWriter(
    private val shard: ShardId,
    private val lease: Lease,
    private val wal: WalWriter,
    private val memtable: MemTable,
) {
    private val pending = Channel<PreparedTx>(capacity = 8192)

    /** 主循环：从队列取事务 → 校验 → 写入 WAL 批次 → 通知提交者 */
    suspend fun run() = coroutineScope {
        val grouper = GroupCommitter(wal, shard, lease.epoch)
        launch { grouper.run() }                       // 独立的组提交协程
        for (tx in pending) {
            if (lease.isExpired()) throw LeaseLost(shard)   // 每批次校验一次租约
            grouper.submit(tx)                               // 非阻塞，返回 CompletableDeferred
        }
    }
}
```

**租约校验的频率**是一个取舍：每个事务校验一次会让 MS 成为性能瓶颈；每批次校验一次则可能在租约刚失效时多写一小批数据。后者是可接受的，因为 fencing（§4.3）保证了这些数据会被忽略。

### 7.3 跨分片事务：2PC with Primary Record

当事务涉及多个分片（例如更新两个不同分区的表，或更新带二级索引的表），需要原子提交。采用 **Percolator 式的 primary record** 协议：

```
Coordinator (任意 CN)      Shard A (写者 cn-1)      Shard B (写者 cn-4)
      │                          │                        │
      │ ① 取 start_ts (预取)      │                        │
      │ ② 写入所有分片的 Prepare   │                        │
      ├───── Prepare(tx, keys) ──▶│ 校验租约                │
      │                          │ 追加 prepare 记录到 WAL │
      │◀──── Prepared ────────────┤                        │
      ├───── Prepare(tx, keys) ──────────────────────────▶ │
      │◀──── Prepared ─────────────────────────────────────┤
      │                          │                        │
      │ ③ 提交决策：取 commit_ts   │                        │
      │    写入 primary 记录      │                        │
      ├── Commit(tx, commit_ts) ─▶│ 追加 commit 记录到 WAL  │
      │      ★ 此刻事务已提交，不可逆 ★                      │
      │◀──── Ack ─────────────────┤                        │
      │                          │                        │
      │ ④ 返回客户端成功（异步通知其余分片）                  │
      │    异步 Commit ──────────────────────────────────▶  │
      │                                                    │
      └─ ⑤ 后台补偿：若某分片 Commit 失败，重试直到成功 ──────┘
```

**为什么这个协议在这里特别好用**：

- **单写者让 Prepare 变得廉价**：不需要在每个分片上争抢锁，因为该分片的写者就是唯一的执行者，`Prepare` 只是往 WAL 写一条记录。
- **primary record 落在 primary 分片的 WAL 里**，而 WAL 在对象存储上，天然持久且可被任何节点读取。这比 Percolator 在 Bigtable 上存锁列更简单——**WAL 就是锁表**。
- **恢复**：任何节点发现一个"已 Prepare 但未见 Commit"的事务时，读 primary 分片的 WAL 查找 commit 记录。有则重放 Commit，无则回滚。这要求 prepare 记录必须包含**足够的信息以完成回滚**（或者：因为 MVCC 的可见性由 `commit_ts` 决定，未提交的版本本来就不可见，回滚只需要清理 lock 记录，不需要撤销数据——**这是一个重要的简化**）。

**与 Cornus 方案的对比**（Cornus, PVLDB 16:379）：Cornus 对 2PC 的核心批评是——**协调者的关键路径上有"一次网络往返 + 两次 eager 日志写"**。它的解法是消除协调者的决策日志，把"真相"定义为所有参与者日志中的投票，并只用一个共享存储的 CAS 原语 `LogOnce()` 保证事务状态最多写一次，从而做到非阻塞。在 Sundial + Azure Blob 上比传统 2PC 降低最多 1.9× 延迟。

本设计选择 primary record（Percolator 式）而非 Cornus，理由是：

| 维度 | primary record（本设计） | Cornus `LogOnce()` |
|---|---|---|
| 关键路径写次数 | Prepare(各分片并行) + Commit(仅 primary) | Prepare 写入所有参与者日志 |
| 依赖的原语 | 普通的对象存储 PUT（无需 CAS） | 需要共享存储的 **CAS 原语** |
| 与单写者的契合度 | **高**——primary 分片的写者本就在追加 WAL，Commit 记录不引入额外往返 | 中 |
| 延迟 | 2 × RTT | 理论上更优 |

**结论**：由于本系统每个分片已由单写者串行化（§7.2），primary 分片的 Commit 记录只是往它本就在写的 WAL 里多追加一条，**不产生额外的网络往返**——这消解了 Cornus 所批评的那次"额外日志写"。因此 primary record 在本架构下是更自然的选择。**但这一结论应在 M2 用原型实测验证**（见 §16.1 Q9）。

**代价与取舍**：跨分片事务的提交延迟 = 2 × RTT（Prepare 并行 + Commit） + 可能的补偿延迟 ≈ 100–200ms。因此系统应**优先把事务限制在单分片内**。这给分区设计提供了指导：**如果业务的主要事务形态是"单用户维度的读写"，按 user_id 分区就能让 95%+ 的事务落在单分片内**。这是一个应该在文档中被强调的应用设计建议（§9.5）。

### 7.4 隔离级别

| MySQL 语法 | 实现 | 说明 |
|---|---|---|
| `READ UNCOMMITTED` | 映射到 `READ COMMITTED`（并告警） | 不支持脏读 |
| `READ COMMITTED` | 每条语句取一个新的 `read_ts` | 语句级快照 |
| **`REPEATABLE READ`（默认）** | 事务级快照（Snapshot Isolation） | 与 InnoDB 默认对齐 |
| `SERIALIZABLE` | SI + 写偏斜检测（SSI） | 检测到危险结构时中止并重试；首版可作为 M4 交付 |

**与 InnoDB REPEATABLE READ 的一个必须说明的差异**：InnoDB 的 RR 通过 next-key lock 在很大程度上避免了幻读；而快照隔离**不阻止写偏斜（write skew）**。对于依赖 InnoDB 加锁语义的应用，迁移到 SI 可能出现新的异常。文档必须在兼容性章节明确警告，并提供 `SERIALIZABLE` 作为出口。

**唯一约束在 SI 下的问题**：两个并发事务插入同一个唯一键，在快照隔离下都可能成功。解决：唯一索引的插入必须走一个"**唯一性校验锁**"——在 MS 的锁表中对 `(index_id, index_key)` 加短程锁，再做存在性检查 + 插入。这会引入一次跨分片的 RTT，但唯一约束本来就无法避免全局协调。

### 7.5 自动重试与幂等

CN 在以下情况会自动重试事务：(a) 租约转移导致写者变更；(b) SSI 检测到危险结构；(c) MS 临时不可用。

重试要求事务**幂等**。做法是为每个事务分配一个 `tx_id = (cn_id, epoch, local_seq)`，并在 WAL 记录中携带。重放时若发现 `tx_id` 已存在，跳过。客户端侧不需要感知重试——但 `LAST_INSERT_ID()` 之类的副作用需要在重试后重新取值。

### 7.6 时间旅行与 PITR

因为 manifest 是不可变的、且历史 manifest 对象不会被 GC（保留窗口默认 30 天，可配置），系统天然支持：

```sql
-- 查询 1 小时前的数据快照
SELECT * FROM orders AS OF TIMESTAMP (NOW() - INTERVAL 1 HOUR) WHERE user_id = 42;

-- 查询某个时间戳的快照
SELECT * FROM orders AS OF TIMESTAMP '2026-09-22 10:00:00';
```

实现：`AS OF T` → 在 manifest 历史中二分查找**第一个 `物理时间 ≥ T` 的 manifest**，以此为文件视图，`read_ts` 取该 manifest 的 `commit_ts_watermark`。**零额外存储成本**（因为历史 manifest 本来就要保留用于 GC 安全窗口），只是多读几个小对象。

**这是一项在传统数据库上很贵、在对象存储上几乎免费的能力**（对比 MySQL 需要 binlog + 全量备份 + 恢复演练）。它应当被作为产品卖点，而不只是一个技术特性。

`FLASHBACK DATABASE TO TIMESTAMP` 的实现是"把 CURRENT 指针指向历史 manifest"——即**回滚是一次指针写操作**，语义上等价于丢弃该时间点之后的所有数据（这些数据在保留窗口内仍可再次通过时间旅行读回）。

## 8. 索引体系

### 8.1 统一抽象（决策 D8）

五种索引看似差异巨大，但在"不可变对象 + manifest 指针"的世界里可以统一：

> **索引 = 一组不可变的索引文件 + 一个 manifest 指针 + 一组查询接口**

```kotlin
interface Index {
    val id: IndexId
    val def: IndexDefinition

    /** 读取索引的当前视图（不可变快照） */
    suspend fun view(readTs: ReadTs): IndexSnapshot

    /** 索引维护：写入路径调用，把行变更转化为索引变更 */
    fun onWrite(change: RowChange, out: MutableIndexMutation)
}

interface IndexSnapshot {
    /** 点查：返回候选主键集合 */
    suspend fun lookup(probe: IndexProbe): RowIdSet
    /** 范围扫描：按索引序返回 */
    suspend fun range(from: IndexKey, to: IndexKey, limit: Int): Sequence<IndexEntry>
    /** 代价估算所需的统计 */
    fun stats(): IndexStats
}
```

**统一带来的收益**（这是选择 D8 的理由）：

| 收益 | 说明 |
|---|---|
| 缓存复用 | 所有索引共享 §6.7 的三层缓存，索引的 `.idx` 元数据同样常驻内存 |
| GC 复用 | 索引文件的 GC 与数据文件走同一套可达性分析 |
| 备份/PITR 复用 | 索引文件的版本由 manifest 指针统一管理，时间旅行同时覆盖索引 |
| 在线构建复用 | 索引构建 = "扫描主表 → 生成不可变文件 → 切换 manifest 指针"，与 compaction 同构 |
| 统一测试 | 一套"并发写 + GC + 时间旅行"的测试可覆盖所有索引类型 |

**统一带来的风险**（必须诚实评估）：不同索引的物理最优结构确实不同，强行统一可能让某个索引实现变扭。缓解方式是：**统一的是"文件 + 指针 + 版本"这一层，而不是文件内部的格式**。每种索引自由定义自己的文件格式（§8.6 的倒排段与 §8.3 的 LSM SST 完全不同）。

### 8.2 索引类型总览与选型

| 索引类型 | 物理实现 | 支持的访问模式 | 何时使用 | 章节 |
|---|---|---|---|---|
| **主索引（聚簇）** | LSM（有序，key=主键） | 点查、范围、前缀 | 恒有，不可选 | §8.2 |
| **二级有序索引** | LSM（key=索引列+主键） | 点查、范围、排序、`ORDER BY` 消除 | 高选择性列、需要范围/排序 | §8.3 |
| **哈希索引** | 段式静态哈希表 + 增量 | **仅等值点查** | 高基数列等值查询，且 B+ 树深度 ≥ 3 | §8.4 |
| **跳数索引** | 数据块级 minmax/set/bloom/ngram | 块级剪枝（不返回行） | 大范围扫描 + 高选择性谓词 | §8.5 |
| **计数索引** | manifest 行数 + `.idx` 块级 `值→计数` | `COUNT(*)` 及其谓词变体，**0 GET** | 分页总数、报表计数 | §8.9 |
| **全文/倒排索引** | 段式 FST + postings | 关键词、短语、布尔、前缀、BM25 排序 | 文本检索 | §8.6 |

**给用户的选型建议**（写进文档的使用者指南）：

```
等值点查为主 + 高基数           → 哈希索引 或 二级有序索引（后者更通用）
需要范围扫描 / ORDER BY / 排序  → 二级有序索引
大表 + 时间/数值范围过滤         → 跳数索引（minmax）★ 性价比最高的选择
低基数枚举列过滤（status 等）    → 跳数索引（set）★ 同时自动获得 0-GET 的 COUNT
分页 / 报表的 COUNT(*)           → 计数索引（§8.9）★ 默认开启
大文本列的 LIKE '%子串%'         → 跳数索引（ngrambloom，仅作剪枝）
自然语言检索 / 相关性排序        → 全文索引（不要用 ngrambloom，见 §8.5）
```

### 8.3 二级有序索引（B+ 树语义）

**对外语义**：等价于 `CREATE INDEX ... USING BTREE`，支持点查、范围扫描、`ORDER BY` 消除、`MIN`/`MAX` 优化。

**物理实现**：一个独立的 LSM 实例。这在语义上是成立的——**LSM 与 B+ 树都是有序索引，对使用者而言可观测的差异只在于读放大与写放大，而不在于正确性**。

| 维度 | 真·B+ 树 | 本系统的 LSM 有序索引 | 影响 |
|---|---|---|---|
| 点查 IO | 3–4 次（树高） | 1–2 次（bloom + 块索引） | **LSM 更优** |
| 范围扫描 | 优秀（叶子链表） | 良好（需归并多层） | B+ 树略优 |
| 写放大 | 低（原地更新） | 高（compaction 重写） | B+ 树优，但对象存储上"写放大"的代价是流量费 |
| 就地更新 | 支持 | 不支持（不可变） | **对象存储上 B+ 树无法直接实现** |

第 4 行是决定性的：**in-place update 的 B+ 树在对象存储上根本无法实现**，因为对象不可原地修改。唯一可行的"真 B+ 树"是 **COW B+ 树**（copy-on-write）：每次更新重写从根到叶的整条路径，产生新对象，根指针切换。

**COW B+ 树的评估**（作为备选保留，见 §16 开放问题）：

| 方面 | COW B+ 树 | LSM |
|---|---|---|
| 一次更新的写放大 | 树高 × 节点大小 ≈ 3 × 16 KB = 48 KB | WAL 记录（几十字节）+ 摊薄的 compaction |
| 点查 IO | 树高 ≈ 3–4 次 GET | 1 次 GET（bloom 过滤 + 块索引） |
| 并发写 | 需要路径锁 | 单写者已串行化 |
| 实现复杂度 | 中 | 中（已有成熟参考） |

**结论：默认使用 LSM 实现有序索引，对外提供 B+ 树语义。** COW B+ 树作为路线图上的可选项（M5+），面向"写极少、读极多、要求极限低读放大"的场景。

**索引键的编码**（必须显式定义，因为它决定索引是否支持前缀扫描）：

```
索引 key = [index_col_1][index_col_2]...[pk]
           每个列编码为  order-preserving bytes：
             - 定长类型（int/bigint/datetime）：大端字节序，保证字典序 = 数值序
             - 有符号整数：符号位取反后大端，使负数排在正数之前
             - 字符串：collation-aware 编码；utf8mb4_general_ci 需转成
                       case-folded + accent-folded 的可比较形式
             - NULL：单独的 NULL 标记字节，排在所有非 NULL 之前（与 MySQL 一致）
           value = 空（covering 索引可内联部分列以避免回表）
```

**`ORDER BY` 消除**：物理计划阶段，若查询的 `ORDER BY` 是某个索引 key 的前缀，且所有前导列都有等值谓词，则直接用该索引的有序性，跳过排序算子。这是二级索引最重要的收益，需要在优化器中实现。

**回表成本与 covering index**：对象存储上的"回表"= 一次额外的点查 = 1 次 GET。因此 **covering index（`INCLUDE` 子句）的价值比在本地数据库上更高**——它可以把 2 次 GET 降到 1 次。优化器应偏好选择 covering 索引，即使其选择性略差。

### 8.4 哈希索引

**用途的诚实评估**：哈希索引只支持等值查询，且现代 LSM 的点查已经只需 1 次 GET。哈希索引的价值场景很窄：

> 在高基数列上做纯等值点查，且该列的有序索引树深较大时，哈希索引能把 1 次"块索引二分 + 数据块读"简化为 1 次"桶读"。

**实现：可扩展哈希（extendible hashing）的段式变体**，契合对象存储的不可变模型：

```
index/{index_id}/
  manifest/CURRENT → { global_depth, buckets: [...], base_version }
  base/{version}/           # 静态基表：一次全量构建的哈希表
    bkt_{bucket_id}.bin     # 每个桶约 64–256 KB，内含 (hash, pk) 条目
  delta/{seq}/              # 增量：把新写入的条目按桶分组，小对象
    bkt_{bucket_id}.bin
  bloom/{version}.bin       # 全局 bloom，快速判定"键根本不存在"
```

- **查找**：`hash(key)` → 定位桶 → GET `base/{v}/bkt_N.bin`（若内存有缓存则 0 次）→ 再叠加读所有 delta 桶 → 按 `commit_ts` 做 MVCC 过滤。
- **分裂**：当某个桶超过阈值，`global_depth++` 并重写该桶（幂等，可重试）。
- **合并（compaction）**：delta 桶数量超过阈值时，把它们合并回 base，生成新的 `base/{version+1}` 并切换 `CURRENT`。

**取舍**：哈希索引**不支持范围扫描**，且需要维护额外的数据结构。**建议默认不自动创建哈希索引**，而是作为 `CREATE INDEX ... USING HASH` 的显式选项，并在文档中说明其适用边界。

### 8.5 跳数索引（Skip Index）

这是**对象存储场景下性价比最高的索引类型**，因为它的收益单位是"省掉的对象存储 GET"，而不是"加速的 CPU 计算"。

**核心思想**：为每个数据文件/数据块维护一个**紧凑的摘要**，在不读取数据的情况下判断"这个块**一定不含**满足谓词的行"。判定为"一定不含"就整块跳过——**这是唯一能在对象存储上把 IO 降到 0 的优化**。

**四种实现**（对齐 ClickHouse 的 skip index 语义，但载体是 `.idx` 对象内的列统计区）：

| 类型 | 摘要内容 | 支持谓词 | 大小占比 | 选择性 |
|---|---|---|---|---|
| **minmax** | 每列 min/max | `<, >, <=, >=, BETWEEN` | ~0.5% | 对单调/聚集数据极佳 |
| **set** | 每列的去重值集合（≤ N 个时） | `=, IN, !=` | ~1–3% | 对低基数枚举列极佳 |
| **bloom_filter** | 每列值的布隆过滤器 | `=, IN` | ~1–2%（10 bits/key） | 对等值查询好 |
| **ngrambloom** | 文本列的 n-gram 布隆过滤器 | `LIKE '%x%'`, 分词后的包含 | ~2–5% | 对模糊匹配好 |

> **⚠️ 一个行业已经纠正过的方向：不要用 bloom 型跳数索引做全文检索。**
>
> ClickHouse 从 v26.2 起已**废弃** `ngrambf_v1` / `tokenbf_v1` 用于全文检索，改用 `text` 索引（真正的倒排索引）。原因是布隆过滤器只能做**存在性剪枝**，无法提供词频、位置、相关性排序——而这些正是全文检索的核心。
>
> 因此本系统的分工必须是明确的：
>
> | 需求 | 用什么 | 不用什么 |
> |---|---|---|
> | 自然语言检索、相关性排序、短语/布尔查询 | **倒排索引**（§8.6） | ❌ ngrambloom |
> | `LIKE '%substring%'` 的子串匹配剪枝 | ngrambloom（**作为剪枝，不返回行**） | — |
> | 枚举列、数值范围过滤 | minmax / set | — |

**与主键 bloom 的区别**（这是一个容易混淆的点，必须在文档中澄清）：

| | 主键 bloom | 跳数索引 bloom |
|---|---|---|
| 位置 | `.idx` 对象内，**每文件一个** | `.idx` 对象内，**每列每块一个** |
| 回答的问题 | "key 是否在这个文件里？" | "这个块里是否存在某行，其 col_c 的值 = v？" |
| 粒度 | 文件 | 数据块 |
| 用于 | 点查路由 | 范围扫描剪枝 |

**查询执行中的使用**：

```
SELECT * FROM events
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-02'   -- minmax 强剪枝
  AND status = 'failed'                                   -- set 强剪枝
  AND message LIKE '%timeout%'                            -- ngrambloom 剪枝
  AND user_id = 12345;                                    -- 主键 bloom

执行计划：
  1. 分区裁剪（§9.2）→ 排除 90% 的分区（元数据操作，0 IO）
  2. 对每个候选文件，读 .idx（通常已常驻内存）
     ├─ created_at 的 minmax 与查询区间无交集 → 跳过该文件（0 IO）★
     └─ status 的 set 不含 'failed' → 跳过该文件（0 IO）★
  3. 对剩下的文件，逐块用列统计剪枝
     ├─ 块级 minmax 判定 → 跳过 90% 的块（0 IO）★
     └─ 仅对存活块发起 range GET
  4. 块内解压、逐行过滤（ngrambloom 在块内进一步剪枝）
```

**收益的量化**（写进 §14 的基准目标）：对于一个有 10 亿行、按月分区、按时间聚集的表，`WHERE created_at BETWEEN 两天 AND status='failed'` 这类查询可以做到**只读 2 个分区中的 3% 的数据块**，即 **从 100 次 GET 降到 3 次 GET**。这是决定性的改进。

**代价**：
- `.idx` 对象大小增加约 3–8%（换取 IO 的数十倍减少）；
- 写入时维护摘要的 CPU 开销；
- **跳数索引不能替代数据过滤**——它只能"排除确定的否定"，不能"确认肯定"。这个语义在实现中必须严格保持，否则会出现漏行。

### 8.6 全文索引与倒排索引（自研，Kotlin）

这是技术含量最高、也最能体现设计特色的一章。选择自研（D10）的理由与代价：

| 维度 | 自研 | 内嵌 Lucene |
|---|---|---|
| MVCC 集成 | 原生：段携带 `commit_ts` 范围，可见性过滤下推到 posting 层 | 困难：Lucene 假设本地目录、假设删除是即时的 |
| 对象存储适配 | 原生：段内文件可独立 GET，postings 分块可按需取 | 需大量 hack：`Directory` 抽象假设随机读写 |
| 中文分词 | 可插拔 | 需引入 `lucene-analyzers-smartcn` |
| 实现成本 | **高**（FST、WAND、BM25、段合并） | 低 |
| 可控性 | 完全 | 受限于 Lucene 的版本兼容与内部 API |

**结论（Q4 已决策）**：**完全自研，不引入 Lucene/Tantivy 兜底**。但**分阶段交付**——先做"能用的正确实现"（暴力扫描 + 简单剪枝），再逐步优化到 block-max WAND。不要一上来就追求极致性能。

> 注意 Q4 决策与"分阶段"并不矛盾：分阶段指的是**实现深度的递进**（先正确后优化），而不是"先用第三方库顶一阵再换掉"。后者被否决的原因见 §16.1：Lucene 假设本地文件系统与"读到即最新"，其 MVCC 集成成本未必低于自研（§8.6.5 的 deletes 位图设计在 Lucene 上几乎无法表达）。

#### 8.6.1 段的结构与对象布局

```
index/{index_id}/
  manifest/CURRENT              # { segments: [...], schema_version, index_version }
  seg/{seg_id}/
    meta.json                   # 段元信息：doc_count, 列定义, commit_ts 范围, 校验和
    terms.fst                   # 词典：term → posting 起始偏移（FST，常驻内存）
    terms.blk                   # FST 的分块副本（FST 过大时的分块加载）
    postings.bin                # 倒排表：每 term 的 docid 列表（delta+varint）
    postings.idx                # 倒排表的块级索引（★ 剪枝用，常驻内存）
    positions.bin               # 位置信息（短语查询、邻近查询）
    norms.bin                   # 每文档的字段长度（BM25 归一化）
    stats.json                  # doc_freq、总文档数、列级 minmax（剪枝用）
    deletes.roar                # 删除位图（RoaringBitmap）
    store.bin                   # 可选：内联文档存储（covering，避免回表）
```

**段的大小目标是 8–64 MiB**（在对象存储上一次 GET 可接受的量级），通过分层合并控制。

#### 8.6.2 倒排表的分块与剪枝

这是让全文检索在对象存储上可用的关键。**如果 postings.bin 是一个整体，查询一个词就必须下载全部 postings——对高频词可能是几十 MB。**

```
postings.bin 的分块布局：

┌──────────────────────────────────────────────────────────┐
│ term="error" 的 posting list（1,000,000 个 docid）        │
├──────────────────────────────────────────────────────────┤
│ Block 0: 128 个 docid │ max_score 上界 8.2 │ 压缩后 96 B │ ← 高命中文档
│ Block 1: 128 个 docid │ max_score 上界 3.1 │ 压缩后 88 B │
│ Block 2: 128 个 docid │ max_score 上界 0.4 │ 压缩后 72 B │ ← 低分，可跳过
│ ...                                                       │
│ Block 7812: ...                                          │
└──────────────────────────────────────────────────────────┘

postings.idx 记录每个 block 的 { offset, length, first_docid,
                                  last_docid, max_score_upper_bound }
```

**Block-Max WAND 的执行流程**：

```
1. 从 terms.fst 得到候选 term 的 postings.idx 偏移（★ 内存操作，0 IO）
2. 加载 postings.idx（通常常驻内存）
3. 用块级的 max_score 上界做 WAND 剪枝：
     维护一个 top-k 堆；对每个 term 的当前块，
     若 (当前块 max_score 之和) ≤ 堆中第 k 名的分数 → 整块跳过，不读取
4. 仅对通过剪枝的块发起 range GET（★ 只取需要的几十到几百字节）
5. 块内解压、算精确 BM25、更新堆、推进游标
```

**效果**：查询一个在 100 万文档中命中 80 万次的高频词，取 top-10 结果，实际只需读取**头几个块的几千字节**，而不是 10 MB 的完整 postings。**这是把全文检索放到对象存储上的可行性前提。**

#### 8.6.3 词典：FST

词典用**有限状态转换器（FST）**存储，提供：

- **精确查找** term → posting 偏移；
- **前缀枚举**（`prefix*` 查询）与**模糊匹配**（Levenshtein 自动机，用于拼写纠错）；
- **紧凑**：FST 对共享前后缀的词典（如中文分词后的词表）压缩率通常在 10–20 倍；
- **可内存映射**：`terms.fst` 通常 < 10 MB / 段，可整体常驻内存。

Kotlin 的实现选择：**自己实现一个最小 FST**（构造 + 遍历 + 前缀查询约 800–1200 行），而不是依赖 Lucene 的内部 `FST` 类（它是 `o.a.lucene.util.fst` 下的公开类但 API 不稳定）。若工期紧张，可先用 `HashMap<String, PostingRef>` + 排序数组作为第一版，再替换为 FST——**接口上要预留这个演进**。

#### 8.6.4 分词与分析链

```kotlin
interface Analyzer {
    fun analyze(field: String, text: String): List<Token>
}
data class Token(val term: String, val position: Int, val startOffset: Int, val endOffset: Int)

// 分析链（可配置）
StandardAnalyzer()   // 英文：小写、去停用词、词干化(Porter)
ChineseAnalyzer()    // 中文：Jieba 分词 / HanLP / n-gram 兜底
NgramAnalyzer(2, 3)  // 兜底：二元、三元组，用于任意子串匹配
```

**中文分词的选择**：JVM 生态有 `jieba-analysis`（结巴的 Java 移植）与 `HanLP`。建议**双模式**：

- **检索模式**：用 Jieba 分词（索引时与查询时用同一套词典），得到合理的词边界；
- **兜底模式**：`ngram(2,3)`，保证任何查询子串都能被匹配到（代价是索引膨胀 3–5 倍）。

对于绝大多数应用，**双模式 + 让用户按字段选择**是最实用的方案，而不是试图做完美分词。

#### 8.6.5 与 MVCC 的集成（本设计的关键差异点）

Lucene 式的"读到即最新"假设在 MVCC 下不成立。集成方案：

**方案：docid 稳定 + 可见性双过滤**

```
段的 docid 是**密集递增**的（0..N-1），与主键的映射存在 store.bin 或一个单独的 docmap 里。
段的 meta.json 记录该段的 commit_ts 范围 [min_ts, max_ts]。

查询时携带 read_ts：
  ┌─ 段完全在 read_ts 之后生成（min_ts > read_ts）
  │    → 整个段跳过（★ 段级剪枝，0 IO）
  ├─ 段完全在 read_ts 之前（max_ts ≤ read_ts）
  │    → 段内所有文档可见（除去 deletes 位图标记的）
  └─ 否则（段跨越 read_ts）
       → 加载 deletes.roar，并对每个候选 docid 做逐行 commit_ts 校验
```

**更新与删除**：由于段不可变，行更新 = 在新段中写入新版本 + 在旧段的 `deletes.roar` 中标记旧 docid。落在 `read_ts` 之前的旧版本仍需可见，因此 **deletes 位图必须携带生效的 commit_ts 范围**，即 `deletes.roar` 实际是一系列 `(commit_ts_range, roaring_bitmap)` 对：

```
deletes.roar 的实际结构：
  [ (ts: 1000..1050, roaring: {...}),      # 在 1000-1050 间被删除的文档
    (ts: 1051..1200, roaring: {...}) ]
读 read_ts=1020 时，只应用第一段位图。
```
这增加了实现的复杂度，但它是**在不可变段上实现 MVCC 的唯一正确方式**。必须在设计阶段就确定，事后无法补救。

#### 8.6.6 段合并（Compaction）

- **触发**：段数超过阈值（默认 16）或小段占比过高。
- **策略**：分层合并（tiered），小段合并成大段；完全被后续版本覆盖的段可以直接丢弃（**这是一次巨大的 GC 机会**——一个被更新了 5 次的文档，其 5 个旧版本可以在合并时一次性消除）。
- **执行**：合并时做真正的**多路归并**（K 路归并 term，再归并 docid 列表），而不是"读出来重新索引"，后者会丢失位置信息且代价高 3–5 倍。
- **写对象**：合并产物是新的段目录，用 multipart upload 流式写入，最后切换 manifest 指针。
- **合并是 IO 密集型的**，与 §6.6 的 LSM compaction 共享同一个带宽预算，避免两者同时抢占带宽。

#### 8.6.7 支持的查询语法

```sql
-- 关键词（BM25 排序）
SELECT id, title, MATCH(content) AGAINST('database storage' IN NATURAL LANGUAGE MODE) AS score
FROM articles WHERE MATCH(content) AGAINST('database storage') ORDER BY score DESC LIMIT 20;

-- 布尔：+ 必须包含，- 必须排除
... AGAINST('+database +object -sql' IN BOOLEAN MODE)

-- 短语查询（需要 positions）
... AGAINST('"object storage"' IN BOOLEAN MODE)

-- 前缀
... AGAINST('data*' IN BOOLEAN MODE)

-- 字段限定与加权
... AGAINST('title:database^2.0 content:storage' IN BOOLEAN MODE)
```

**BM25 参数**：`k1 = 1.2`、`b = 0.75`（默认，可配置）。评分所需的 `doc_freq` 从各段的 `stats.json` 汇总——注意**跨段评分需要全局统计**，因此段合并时也要合并统计信息。这是一个容易出错的点：如果各段用自己的局部 `doc_freq`，同一文档在不同段中的分数尺度不一致，排序会错乱。

**首版的简化**：先实现 `IN BOOLEAN MODE`（无需全局统计，正确性容易保证），再实现 `IN NATURAL LANGUAGE MODE` + BM25（需要全局统计）。这是有意的分阶段，因为布尔模式的正确性更容易测试。

### 8.7 在索引构建（Online Index Build）

`CREATE INDEX` 在一张已存在的表上：

```
1. DDL 提交到 MS → Catalog 中标记索引为 "BUILDING" 状态
2. 选择一个 CN 作为构建者，从 MS 取得一个构建任务
3. 扫描主表的所有分片（用 read_ts = 构建开始的快照）
   → 流式生成索引文件（复用 LSM compaction 的写入路径）
   → 中途分片写入的新数据：记录 "delta 区间"（从 read_ts 之后的所有 WAL）
4. 索引文件就绪 → 切换索引 manifest 指针 → 状态置为 "ACTIVE"
5. 重放 delta 区间（read_ts 之后的写入）到索引
6. 完成 → Catalog 中索引可见，`information_schema.STATISTICS` 可查
```

**关键点**：步骤 3 的扫描是**快照读**，因此不需要锁表；步骤 5 的 delta 重放是有限且可追上的（因为写入速率有限）。这与 MySQL 的 `ALGORITHM=INPLACE` 语义对齐。

**失败处理**：构建中断时，已生成的索引文件成为孤儿对象，由 GC 回收；Catalog 中的索引保持 "BUILDING"，可重试（幂等）。

### 8.8 索引的写放大与代价

必须诚实说明：**每一个二级索引都会让写入变慢、变贵**。

| 索引数 | 单次写入的额外对象存储操作 | 延迟影响 |
|---|---|---|
| 0（仅主键） | 0（都进同一个 WAL 批次） | 基线 |
| 1 | 0（索引变更写入同一个 WAL，只是记录更多） | +5–15% |
| 5 | 0（同上）+ compaction 数据量 ×5 | +30–60% |

因为索引变更与主数据变更**共享同一个 WAL 批次、同一个分片写者**，它们不产生额外的 PUT 请求。但 compaction 阶段需要重写的数据量按索引数线性增长。**这是建议用户谨慎建索引的量化依据**，应写进使用者指南。

### 8.9 计数优化：让 COUNT 不读数据

**这是本项目最重要的性能优化之一**，因为 `SELECT COUNT(*)` 是对象存储上**最贵又最常见**的查询：朴素实现扫描全表，一个 10 亿行的表就是**数万次 GET 与数百 GB 流量**——成本上完全不可接受。

（MySQL/InnoDB 同样有此问题，它靠"选最小的二级索引做全索引扫描"缓解；但那在对象存储上依然昂贵。）

**目标：让 `SELECT COUNT(*)` 及其常见谓词变体做到 0 次数据 GET，且结果精确。**

#### 8.9.1 机制 1：manifest 上的精确行数（覆盖 `T = now`，最常见路径）

```jsonc
// manifest 中新增
"row_count": {
    "exact": 8421332,        // commit_ts_watermark 处的精确可见行数
    "at_ts": 900123
}
```

由**单写者**维护——它串行化了所有提交，因此知道每个事务的净行数变化（`+3` / `-1` / `0`）。每次 flush / manifest 切换时把增量折叠进 `exact`。

查询 `T ≥ at_ts` 的计数 = `exact` + WAL 中 `(at_ts, T]` 区间的净变化（来自 MemTable，**纯内存**）。

**代价：写者需要判断"这次写入是新键还是覆盖"。** 判断方式：

| 情况 | 成本 |
|---|---|
| 表带二级索引 | **无额外成本**——维护索引本来就要回表取旧值 |
| 无二级索引，bloom filter 判定"一定不存在" | 内存操作，**0 GET** |
| 无二级索引，bloom 假阳性 | 需精确判定，**延迟到 flush 时批量解析**（此时正在读这些数据，摊薄为 0） |

> 设计取舍：这条优化让**写入路径承担了一点额外成本**，换取读取路径的极大收益。考虑到本项目面向"读多写少"场景（§0.3），这是一笔划算的交易。**但它必须是可关闭的**（`exact_count = on/off`，表级），因为极端写密集的表可能不愿意付这个成本。

#### 8.9.2 机制 2：文件级 MVCC 感知计数（覆盖 `T` 在过去 / 长事务快照）

扩展 `.idx` 对象的元数据区（§6.4）：

```
per-file:  { row_count, tombstone_count, min_commit_ts, max_commit_ts }
per-block: { row_count, tombstone_count, min_commit_ts, max_commit_ts }
```

> ⚠️ **实现期间修正的一处推理错误**
>
> 本节初稿声称：「因为单写者，写入天然串行 ⇒ 单个文件内 `commit_ts` 沿块序单调不减，
> 因此一个 `read_ts` 至多切到一个块」。**这个推理是错的**——一个 MemTable flush 出的
> 文件，其所有块共享同一段时间窗口，`ts` 在块之间并不单调（compaction 产物更是如此）。
>
> 正确且更简单的做法在下面，**依然精确、依然 0 次 GET**，只是代价从「至多一个跨界块」
> 变成「每块一张小表」。

**正确做法：在 `.idx` 的每个块内记录「`ts` → 截至该 ts 的存活条目累积数」**（`tsCounts`）。

于是对 `read_ts = T`，每个块只需判断三种情况：

```
max_commit_ts ≤ T   →  整块可见   → 贡献 block.rows                 （纯元数据，0 GET）
min_commit_ts > T   →  整块不可见 → 贡献 0                          （0 GET）
跨越 T              →  在 tsCounts 上二分查找 → 精确的累积计数       （0 GET）
```

⇒ **完全不需要读取数据块**，且不受块数影响。代价是每块约 +1% 的元数据体积——
因为一个提交批次会产生大量同 ts 的条目，块内**不同 ts 的个数远小于条目数**。

实测（`yb-bench`）：`.idx` 占总数据量的 **6.9%**，其中 `tsCounts` 是主要成分。
在「一事务一行」这类极端负载下不同 ts 会退化到 1:1，因此该表有上限
（默认每块 1024 个 ts 分桶），超过就放弃收集——计数路径随即回退到精确扫描，
**而不是给出估算值**（§8.9.7）。

#### 8.9.3 机制 3：LSM 多版本去重（最容易出错、也最必须先想清楚的地方）

**必须解决**：LSM 中同一个 key 可能存在于多个层，`Σ file.row_count` 会**重复计数**。

| 层 | 键重叠性质 | 去重方式 |
|---|---|---|
| **MemTable** | 内存中天然唯一 | 无需处理 |
| **L0** | 文件间**可能重叠**，且与 L1+ 重叠 | 需要去重 |
| **L1..Ln** | **leveled 不变式保证 key 在 L1+ 中至多出现一次** | **无重复，直接求和** |

```
exact_count(T) = Σ_{L1..Ln} visible_rows(f, T)        ← 纯元数据，无重复
               + dedup_count(L0 ∪ MemTable, T)
```

于是**机制 1 是主路径**（写者维护时已完成去重），机制 2 只在需要**历史快照**时启用；两者在 `T = now` 时的结果必须一致——**这是一条必须写进测试的不变式**。

> **⚠️ 这条优化给 LSM 的 compaction 策略增加了一个硬约束：**
> **从 L1 开始就必须保证"层内 key 不重叠且跨层唯一"（即 leveled），不能使用 tiered/universal 的 L1。**
> 因为机制 3 的"直接求和"完全依赖这个不变式。若未来为降低写放大想改用 tiered，**必须先解决这里的重复计数问题**。这条约束需同步写入 §6.6。

L0 的去重（回退路径）：L0 文件数有界（compact 触发阈值，默认 4），用**内存中的 bloom filter** 做存在性判定——bloom 判定"一定不存在"的键直接计数，其余走精确路径。因为 L0 小，这条路虽不完美但代价有界。

#### 8.9.4 机制 4：带谓词的计数（扩展跳数索引）

`SELECT COUNT(*) FROM t WHERE status = 'failed'` —— 这是**分页 UI 最常见的查询**（前端要显示"共 N 条"）。

把 §8.5 的 **set 跳数索引**从"值集合"扩展为"**值 → 计数**"：

```
.idx 中 status 列的块级索引：
  { pending: 42, failed: 118, done: 902 }      // 每个数据块内的值分布
```

⇒ `COUNT(*) WHERE status='failed'` = **纯内存求和，0 GET**

**适用边界（必须显式，否则会 OOM）**：

| 谓词类型 | 用哪个机制 | 说明 |
|---|---|---|
| 低基数列等值（`ndv` 低于阈值） | **本机制** | 内存占用 ∝ `ndv × 块数`；`ndv` 从 `stats/` 读取，超阈值则不建 |
| 高基数列等值（如 `user_id`） | 主键/索引点查路径（§8.3） | ~2 GET |
| 范围谓词（`ts BETWEEN a AND b`） | 块级直方图近似，或退回机制 2 + minmax 剪枝 | 精确值需读存活块 |
| 无谓词 | 机制 1 | 0 GET |

#### 8.9.5 机制 5：分区级快速路径

对分区表，若查询覆盖整个分区且 `T = now`，直接从 `stats/table/{tid}/partitions.v{n}.json`（已在内存中，§9.2）求和 → **0 GET，0 元数据遍历**。

这是"按月分区 + `COUNT(*)`"这类报表查询的理想路径。

#### 8.9.6 优化器集成

```
EXPLAIN SELECT COUNT(*) FROM orders\G
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: orders
         type: METADATA_COUNT              ← 不扫描数据
possible_keys: NULL
          rows: 8421332
        Extra: Using metadata count (manifest, exact, 0 object reads)
```

**规则**：优化器**必须始终优先选择元数据计数路径**，绝不把 `COUNT(*)` 计划成全表扫描。这是 §10.2 代价模型的一个特例——既然元数据路径的代价是 0 GET，它**永远**优于扫描，不需要代价比较。

`EXPLAIN` 必须如实显示走了哪条路径，让使用者能验证优化是否生效。

#### 8.9.7 一致性要求：必须精确，不允许悄悄近似

MySQL 的 `COUNT(*)` 是**精确**的（InnoDB 扫描最小的索引）。用户拿它做分页总数、做业务对账。因此：

> **默认路径必须返回精确值。** 近似计数只允许通过**显式语法**启用，且必须在结果中可辨识：
> - `APPROX_COUNT(DISTINCT x)` —— 用 per-file HyperLogLog 合并 → 0 GET
> - `APPROX_COUNT(*)` —— 明确标注为估算

如果某条路径无法保证精确（例如关闭了 `exact_count` 且需要历史快照），**必须回退到精确扫描，而不是悄悄返回一个估算值**。这是一个"宁可慢，不可错"的地方——分页数字对不上是用户信任崩塌的经典起因。

#### 8.9.8 收益量化

| 查询（10 亿行表 / 100 个数据文件 / 每文件 1000 块） | 朴素实现 | 本设计 | 提升 |
|---|---|---|---|
| `SELECT COUNT(*) FROM t` | ~100,000 GET / 数十 GB | **0 GET** | ∞ |
| `SELECT COUNT(*) FROM t WHERE status='failed'` | ~100,000 GET | **0 GET**（机制 4） | ∞ |
| `SELECT COUNT(*) FROM t`（按月分区，查整月） | ~8,000 GET | **0 GET**（机制 5） | ∞ |
| `SELECT COUNT(*) FROM t AS OF 1 小时前` | ~100,000 GET | **≤ 跨越 T 的文件数**（通常 ≤ 5） | ~20,000× |
| `SELECT COUNT(*) FROM t WHERE user_id = 42` | ~100,000 GET | ~2 GET（索引点查） | ~50,000× |
| `COUNT(DISTINCT user_id)`（精确） | 全扫 | 索引扫描 | — |
| `APPROX_COUNT(DISTINCT user_id)` | 全扫 | **0 GET**（HLL 合并） | ∞ |

#### 8.9.9 实现代价与风险

| 项 | 说明 |
|---|---|
| `.idx` 对象膨胀 | 新增 per-block 的 `row_count`/`tombstone_count`/`commit_ts` 约 **+8–12%**（原有列统计约 15%，总量仍 < 30%） |
| 写路径成本 | 开启 `exact_count` 时，无二级索引的表需做存在性探测（多数为内存 bloom 检查） |
| **正确性风险** | **机制 3 的去重是本节最易出错处**，且错误表现为"数字悄悄偏小/偏大"，不会报错。必须用**属性测试**覆盖：随机写入/删除/compaction 后，元数据计数与全表扫描计数**必须逐次相等** |
| compaction 约束 | 强制 L1+ leveled（§8.9.3），与 §6.6 的写放大优化存在张力 |
| 关闭开关 | `exact_count=off` 时必须**回退到精确扫描**，绝不返回估算值 |

## 9. 分区与数据分布

### 9.1 分区策略与 MySQL 语法对齐

支持 MySQL 的分区语法，语义保持一致：

```sql
CREATE TABLE orders (
    id        BIGINT NOT NULL,
    user_id   BIGINT NOT NULL,
    created_at DATETIME NOT NULL,
    amount    DECIMAL(12,2),
    PRIMARY KEY (id, created_at)
)
PARTITION BY RANGE (TO_DAYS(created_at)) (
    PARTITION p2026q1 VALUES LESS THAN (TO_DAYS('2026-04-01')),
    PARTITION p2026q2 VALUES LESS THAN (TO_DAYS('2026-07-01')),
    PARTITION p2026q3 VALUES LESS THAN (TO_DAYS('2026-10-01')),
    PARTITION pmax    VALUES LESS THAN MAXVALUE
);

-- 或哈希分区（本系统推荐的默认，见 §9.3）
PARTITION BY HASH (user_id) PARTITIONS 8;

-- 或列表分区
PARTITION BY LIST (region) (
    PARTITION p_cn VALUES IN ('cn', 'hk'),
    PARTITION p_us VALUES IN ('us', 'ca')
);
```

| 类型 | 表达式 | 分区数 | 支持的裁剪 |
|---|---|---|---|
| `RANGE` | `TO_DAYS()`、`YEAR()`、列引用 | 静态列举 | 区间交集 |
| `LIST` | 列引用 | 静态列举 | 等值/IN 集合 |
| `HASH` | 整数表达式 | `PARTITIONS n` | **仅等值** |
| `KEY` | 任意列（内部哈希） | `PARTITIONS n` | **仅等值** |

### 9.2 分区裁剪

裁剪发生在**优化器**阶段，且**完全是元数据操作**（原则 P3）。

```
stats/table/{table_id}/partitions.v{version}.json
{
  "partitions": [
    { "name": "p2026q1", "shard": "p_1", "row_count": 8421332,
      "min_created_at": "2026-01-01T00:00:00", "max_created_at": "2026-03-31T23:59:59",
      "size_bytes": 412000000, "object_count": 84 },
    { "name": "p2026q2", ... }
  ],
  "crc": "..."
}
```

- 该对象**常驻内存**（一个表的分区统计通常 < 100 KB）；
- `WHERE created_at BETWEEN '2026-02-01' AND '2026-02-15'` → 二分查找命中 `p2026q1`，排除其余分区；
- 被裁剪掉的分区**不产生任何 IO**。

**裁剪粒度是三层递进的**，这是一个应该被明确表述的设计：

```
分区裁剪 (元数据对象)  →  文件裁剪 (manifest + .idx 的 minmax)  →  块裁剪 (.idx 的列统计)
   省掉 90%+ 的 IO          再省掉 80% 的 IO                      再省掉 90% 的块读
```

三层叠加，一个选择性为 0.1% 的查询最终可能只读原始数据量的 **0.01%**——这是在对象存储上做大表查询的唯一可行路径。

**层级的结构（对照业界已验证的三层模型）**：

| 层 | 载体 | 决策 | 本系统的对应 |
|---|---|---|---|
| L1 分区级 | manifest list 的分区字段 min/max | 排除整个分区 | `stats/.../partitions.v{n}.json` |
| L2 文件级 | 每个文件的列级 lower/upper bound + null count | 排除整个文件 | manifest 中的文件条目 + `.idx` 的 Header |
| L3 块级 | 行组（row group）级 min/max + bloom | 排除数据块 | `.idx` 的列统计区（§8.5） |

参照 Iceberg 官方文档给出的实测例子：**240 个文件被裁剪到 5 个，约 98% 的 IO 被消除**。本系统通过把 L2/L3 的元数据独立成 `.idx` 对象（§6.4），使前两层的判定**完全在内存中完成、零 IO**，这一点比 Iceberg 更进一步（Iceberg 通常需要 GET 一次文件 footer）。

> **⚠️ 一个必须向使用者强调的前提：min/max 剪枝的效力完全取决于数据是否按该列有序或聚集。** 如果数据写入时完全乱序，每个文件的 min/max 都会覆盖全域，索引就退化为"永远无法剪枝"。
>
> 因此本系统应当提供**聚簇提示**机制——让用户能声明"表按 `created_at` 聚集"，写入时据此调整 L0→L1 的 compaction 边界，使每个文件的时间范围尽量窄。这是把"统计信息有效"从运气变成设计的必要手段。

### 9.3 分区即写入分片（决策 D11）

这是本设计中一个**自然且优雅**的对应关系：MySQL 的"分区"在语义上就是"同一张表的独立物理子集"，而本系统的"分片"正是"独立的存储与写入单元"。两者对齐后：

| 性质 | 非分区表 | 分区表（n 个分区） |
|---|---|---|
| 写者数量 | 1 | **n**（每个分区一个租约） |
| 写入并行度 | 1× | **n×** |
| 单次跨分区事务 | — | 需要 2PC（§7.3） |
| 单个分区损坏 | 表不可用 | 仅该分区不可用 |
| Compaction 并行 | 1× | n× |
| 单分区数据量 | 全部 | 1/n（manifest 更小，读放大更低） |

**给使用者的建议（应作为默认推荐写进文档）**：

> 任何预计超过 10 GB 或写入 QPS 超过 200 的表，**都应该分区**。
> 分区键的选择应当使**绝大多数事务落在单个分区内**——通常是业务的主查询维度（如 `user_id`、`tenant_id`、`org_id`）。
> `PARTITION BY HASH(user_id) PARTITIONS 8` 是绝大多数 SaaS 应用的合理默认。

这背后的原则值得单独强调：

> **分区键 = 事务边界 = 写入并行度。** 选对了分区键，跨分区事务就消失了，系统退化为"多个互不干扰的单写者分片"，这是最容易正确、最容易运维的形态。

### 9.4 分区管理 DDL

```sql
ALTER TABLE orders ADD PARTITION (PARTITION p2026q4 VALUES LESS THAN (...));
ALTER TABLE orders DROP PARTITION p2023q1;       -- ★ 极快：删除元数据 + 异步 GC 对象
ALTER TABLE orders REORGANIZE PARTITION pmax INTO (...);
ALTER TABLE orders TRUNCATE PARTITION p2023q1;
ALTER TABLE orders EXCHANGE PARTITION ...;       -- M5+
```

**`DROP PARTITION` 在对象存储上是一次几乎免费的操作**——因为它只是从 manifest 中移除引用，随后由 GC 异步清理对象。对比传统数据库需要 `DELETE + OPTIMIZE` 或整表重建，这是一个显著的运维优势，应当作为**冷数据归档的首选手段**推广：

```sql
-- 冷数据归档模式：按月分区 + 定期 DROP 或下沉到低频存储层
ALTER TABLE logs PARTITION BY RANGE (TO_DAYS(ts)) (...);  -- 建议分区粒度按保留期/24 决定
-- 保留 90 天 → 每天一个分区 → DROP PARTITION 即为归档
```

### 9.5 再平衡

分区一旦创建，其**数据归属是确定的**（由分区函数决定），因此**不存在传统分布式数据库的分裂/迁移（split/merge）问题**。

**这是一个被低估的优势**：`PARTITION BY HASH(user_id) PARTITIONS 8` 意味着 `hash(42) = 3` 永远成立，数据永远在分片 3。没有任何"数据搬迁"、没有任何"rebalance"、没有任何"迁移期间的性能抖动"。

代价是**扩容需要显式的 REORGANIZE**：

```sql
-- 从 8 个分区扩到 16 个，需要重写数据
ALTER TABLE orders REORGANIZE PARTITION p0, p1, ..., p7 INTO (
    PARTITION n0, PARTITION n1, ..., PARTITION n15
);
```
这是一个在线操作（新分区作为新分片构建，完成后切换原子指针），但会消耗带宽。**建议在表创建时就规划足够的分区数**（宁多勿少——32 个分区在 1 GB 数据下也几乎没有额外开销，因为空闲分区不产生请求）。

### 9.6 单表数据量的边界

对象存储方案下，单表（或单分区）的规模上限主要由**manifest 大小**和**读放大**决定：

| 单表/单分区数据量 | manifest 文件数（L1+） | manifest 大小 | 点查 IO | 评价 |
|---|---|---|---|---|
| ≤ 10 GB | ~20 | < 100 KB | 1 GET | 舒适 |
| 100 GB | ~200 | ~1 MB | 1–2 GET | 良好 |
| 1 TB | ~2000 | ~10 MB | 2–3 GET（manifest 分片加载） | 需要分区 |
| 10 TB | — | — | — | **必须分区**，否则 manifest 成为瓶颈 |

**结论**：单分区建议不超过 100 GB。超过则分区；分区数不够就用 `PARTITION BY RANGE` 按时间继续切。

## 10. SQL 引擎

### 10.1 分层

```
SQL 文本
   │
   ▼  Parser (ANTLR4, MySQL 方言)          → AST
   │
   ▼  Binder / Analyzer                     → 绑定 Catalog 的 LogicalPlan
   │     · 名字解析、类型检查、权限校验、视图展开
   │
   ▼  Optimizer                             → PhysicalPlan
   │     · RBO: 谓词下推（★ 含下推到 skip index / 分区裁剪）
   │           常量折叠、子查询解关联、LIMIT 下推
   │     · CBO: 基于 stats/ 的统计信息选择索引与连接顺序
   │
   ▼  Executor (协程 + 向量化)               → 结果集
   │     · 算子: TableScan / IndexScan / FullTextScan /
   │            Filter / Project / HashJoin / Sort / Limit / Aggregate
   │
   ▼
 MySQL 协议层
```

**为什么用 ANTLR4**：MySQL 语法（尤其是 DDL、分区、类型转换）有大量边角，手写递归下降的维护成本高。用 ANTLR4 并参考 StarRocks/Doris 的 MySQL 方言文法（两者都是 ANTLR4，且久经考验）可以节省数月的解析器调试。

**Kotlin 协程与向量化的结合**：算子实现为 `suspend` 函数，消费/产出行批次（`RowBatch`，默认 1024 行）。协程在对象存储 IO 挂起时不占用线程，天然适配"大量并发 range GET"的场景。

```kotlin
abstract class Operator {
    abstract suspend fun open(ctx: ExecContext)
    abstract suspend fun next(): RowBatch?   // null = EOS
    abstract suspend fun close()
}

/** 对象存储上的并行预取扫描：把 range GET 的并发度拉满 */
class ParallelPrefetchScan(
    private val blocks: List<BlockRef>,
    private val concurrency: Int = 8,          // 可配置，默认按带宽/延迟估算
) : Operator() {
    private val channel = Channel<RowBatch>(capacity = concurrency * 2)
    override suspend fun open(ctx: ExecContext) = coroutineScope {
        blocks.chunked(concurrency).forEach { group ->
            launch { group.forEach { fetchAndDecode(it, channel) } }
        }
    }
}
```

### 10.2 优化器：对象存储场景下的特殊规则

CBO 的代价模型与本地数据库有**本质差异**，必须显式建模：

| 代价项 | 本地数据库 | YangBase |
|---|---|---|
| 顺序读一个块 | ~0.1 ms | **~5–20 ms**（GET RTT） |
| 随机读一个块 | ~1 ms（寻道） | **~5–20 ms**（无寻道差异！） |
| 请求费用 | 无 | **每次 GET/PUT 计费** |
| 网络流量 | 无 | **出网流量计费** |
| CPU 计算 | 相对昂贵 | **相对便宜**（相对一次 GET） |

**由此导出的优化规则：**

- **R1：减少 GET 次数 >> 减少传输字节数。** 代价模型以"预计对象存储请求数"为主成本项，而不是以"扫描行数"。一次 GET 取 4 KB 和取 64 KB 的代价几乎相同。
- **R2：偏好 covering index。** 回表 = 额外一次 GET，代价极高（§8.3）。即使用选择性略差但包含所需列的索引，通常也更优。
- **R3：偏好能触发 skip index 的谓词顺序。** 把 minmax/set 选择性最高的列放在最外层扫描阶段。
- **R4：并行度是廉价的。** 把 100 个块分成 8 路并发，总延迟从 100×RTT 降到 13×RTT，而代价只是少量并发。优化器应主动提高并行度（受配置的并发上限约束）。
- **R5：大结果集要流式返回。** 不允许在内存中物化百万行——对象存储的带宽允许快速扫描，但内存会爆。所有算子必须支持流式与背压。
- **R6：`COUNT(*)` 永远走元数据路径，不做代价比较。** 见 §8.9.6——元数据计数的代价是 0 GET，因此它**永远**优于扫描，特化为一条硬规则而非代价估算。`EXPLAIN` 必须显示 `type: METADATA_COUNT` 以便验证。

### 10.3 统计信息

`stats/` 下的统计由**后台任务**周期性收集，存放在对象存储上：

```json
{
  "table_id": 1001, "partition": "p3", "version": 42,
  "collected_at": "2026-09-22T10:00:00Z",
  "row_count": 8421332,
  "columns": {
    "user_id":    { "ndv": 1200000, "null_count": 0, "min": 1, "max": 9999999,
                    "histogram": {"buckets": 32, "type": "equi-depth"} },
    "status":     { "ndv": 7, "null_count": 120,
                    "freq": {"pending": 42000, "failed": 118000, ...} },
    "created_at": { "min": "2026-01-01T00:00:00", "max": "2026-06-30T23:59:59" }
  }
}
```

**统计信息的收集成本**：不能全表扫描（那是昂贵的 GET）。方案是**从索引文件/数据文件的摘要中聚合**——`.idx` 对象里已经有每块的列 min/max、NDV 近似（HyperLogLog 草图）与直方图草图。收集统计 = **读取所有 `.idx` 对象**（它们小且大部分已常驻内存），而**不读任何 `.data`**。这是"对象存储原生"的统计收集方式，成本比传统 `ANALYZE TABLE` 低 1–2 个数量级。

`ANALYZE TABLE` 语义：触发一次这样的聚合，并更新 `stats/` 下的版本化对象。

#### 11.1.1 已知的协议陷阱（来自现有实现的教训）

这些是**已经被别人踩过、会直接导致工具链不可用**的坑，实现时必须逐条覆盖：

| # | 陷阱 | 后果 | 应对 |
|---|---|---|---|
| **T1** | **`character_set_results` 默认为 NULL**（Connector/J 会发 `SET character_set_results = NULL`） | 语义是"按列返回原始字节"。若实现不当，所有中文都是乱码 | 要么完整支持按列字符集，要么强制 utf8mb4 并在其余位置显式拒绝 |
| **T2** | **prepared statement 的字符集必须按 `EXECUTE` 时刻的会话状态解码** | TiDB 有过真实 bug：`SET NAMES gbk` 后 prepare/execute，再切回 utf8mb4 读出乱码 | `PREPARE` 与 `EXECUTE` 之间会话状态（charset / `sql_mode` / `ANSI_QUOTES`）**可能漂移**，每次 `COM_STMT_EXECUTE` 前重新探测 |
| **T3** | **binary protocol 的结果集编码比文本协议麻烦得多** | 任何对结果值的改写都必须**重算 length 与 NULL bitmap** | `COM_STMT_EXECUTE` 含 `stmt_id / flags / iteration_count / null_bitmap / new_params_bound_flag`，类型只在首次执行时告知；建议把"值编码"做成独立的可单元测试组件 |
| **T4** | **图形化客户端在连接期就会发元数据查询** | **Navicat 在没有任何 schema 时会直接连不上**；DataGrip 需要开启 "introspect using JDBC metadata" | 必须在 M0 就提供一个默认 schema（如 `information_schema` 之外的引导库），否则无法用图形工具调试 |
| **T5** | **`information_schema` 的覆盖度决定工具链可用性** | ShardingSphere-Proxy 官方承认"对 information_schema 支持有限，图形化客户端可能报错，建议用命令行客户端" | 参考 §11.2 的最小可用面清单；**把它作为 M2 的验收项而非收尾工作** |
| **T6** | 服务端游标需要 `CURSOR_TYPE_READ_ONLY` + `COM_STMT_FETCH` | 大结果集客户端报错 | M2 实现，与流式返回（§10.2 R5）配套 |

### 11.3 明确的限制清单（必须写进用户文档）

**不支持**（会返回明确的错误码而非静默失败）：

- 存储过程、函数、触发器、事件调度器、游标
- 视图的可更新性（视图本身支持只读）
- 外键的 `ON DELETE CASCADE`（外键约束可声明并校验，但级联由应用层实现；M4 评估）
- `LOAD DATA INFILE`（提供 `LOAD DATA` 的客户端流式变体）
- `SELECT ... INTO OUTFILE/DUMPFILE`
- 空间索引与 `GEOMETRY` 函数（M5）
- X Protocol / MySQL Shell 特有功能
- 复制相关：`CHANGE MASTER TO`、`START SLAVE`、`binlog`

**语义有差异**（需要在文档中高亮警告）：

| 项 | MySQL/InnoDB | YangBase | 影响 |
|---|---|---|---|
| **默认 RR 的幻读防护** | next-key lock | 快照隔离（不防写偏斜） | ⚠️ **迁移风险最高的一项**，见 §7.4 |
| 自增主键 | 连续、可回滚 | 采用**分段预取**（每 CN 预取 1000 个），**可能不连续且有空洞** | ⚠️ 依赖连续性的业务会受影响 |
| `SELECT ... FOR UPDATE` | 行锁 | MS 上的行锁表，跨分片有额外 RTT | 语义一致，性能不同 |
| DDL | 部分场景锁表 | 全部在线（元数据操作） | ✅ 更优 |
| 事务隔离下的唯一约束 | next-key lock | 唯一性校验锁（跨分片 RTT） | 性能差异 |
| `ORDER BY` 的 NULL 位置 | NULL 最小 | 与 MySQL 对齐 | — |
| `LIKE` 的大小写敏感 | 依赖 collation | 与 collation 对齐 | — |

### 11.4 自增主键的分段分配

MySQL 的自增是全局连续且在服务端集中分配。在无共享的架构下这会成为瓶颈。方案：

```
MS 维护 sequence 的 high_watermark。
CN 请求自增段 → MS 返回 [base, base+1000) 并推进水位。
CN 本地用完后再申请下一段。
```

**后果**：多个 CN 交替插入时，自增值会跳跃；事务回滚会留下空洞。这与 MySQL 8.0 的 `innodb_autoinc_lock_mode=2`（交错模式）行为一致，MySQL 文档明确说明该模式下自增值不保证连续。**但依赖 `AUTO_INCREMENT` 连续性的应用会受影响，必须在兼容性文档中显式警告。**

## 12. 生命周期与运维

### 12.1 部署拓扑

| 角色 | 规格建议 | 数量 | 生命周期 |
|---|---|---|---|
| **CN（计算节点）** | 2–8 vCPU / 8–32 GiB / 本地 NVMe（缓存用） | 1–N，按需 | **可随时销毁重建**，可抢占/Spot |
| **MS（元数据服务）** | 2 vCPU / 4 GiB | **3**（Raft 多数派） | 可跨可用区分布；可小规格常驻 |
| **对象存储** | 全托管 | — | 与计算完全解耦 |

**成本套利的操作方式**（这才是原始需求的落点）：

```
节假日/大促 → 购入大额折扣的 1 年期 ECS，把 CN 与 MS 迁上去
                （CN 无状态 → 直接销毁旧的、拉起新的，零数据迁移）
到期续费贵  → 换到新一轮折扣实例，或缩容到最小规格按需运行
                （MS 也可以迁——它的状态在对象存储上，3 节点滚动重建，
                  全程 < 1 分钟不可用窗口）
业务低谷     → CN 缩到 1 个最小实例；或干脆停掉，用 Serverless 按请求拉起
```

**规划要点**：MS 是唯一不能"完全停掉"的角色（它提供写入所需的 TSO 与租约）。但它的规格需求极低（§13 给出成本），且在 §4.7 的降级模式下甚至可以由对象存储承担。

### 12.2 故障模型与恢复

| 故障 | 影响 | 恢复机制 | RTO | RPO |
|---|---|---|---|---|
| **单个 CN 崩溃** | 该 CN 上的查询失败；它持有的分片写者身份失效 | 客户端重连到其他 CN；租约超时后新写者接管 | 10–20s（写）/ 立即（读） | 0 |
| **CN 所在的可用区故障** | 同上，范围更大 | 同上，其他区接管 | 10–20s | 0 |
| **MS 单节点崩溃** | 无（Raft 多数派仍在） | 剩余 2 节点继续服务；重建第 3 个节点 | 0 | 0 |
| **MS 多数派故障** | 写事务与 DDL 不可用；**只读事务仍可用**（TSO 预取） | 重启 MS 节点，从对象存储快照恢复 | 10–30s | 0 |
| **对象存储不可用** | 全系统不可用 | 等待云厂商恢复（由 SLA 兜底） | 取决于云 | 0 |
| **对象存储单对象损坏** | 该对象读取失败 | WAL 记录级 CRC 跳过坏记录；数据块级 CRC 触发从其他副本重读（对象存储内部自动） | 立即 | 0（对象存储自带冗余） |
| **单 Region 故障** | 该 Region 全不可用 | 跨 Region 只读副本接管（异步，RPO>0） | 分钟级 | 秒级 |

**关键结论**：**RPO 恒为 0**（在单 Region 内）——因为所有已提交的数据都在对象存储上，而对象存储自身提供多副本与 11 个 9 的持久性。这是本架构相比"自建多副本"的最大收益：**不需要自己实现复制协议，也就不需要自己证明它的正确性**。

### 12.3 备份与时间点恢复（PITR）

由于历史 manifest 不可变且保留窗口内不删除：

| 恢复能力 | 实现 | 成本 |
|---|---|---|
| **时间点恢复（任意秒级）** | 找到 ≤ 目标时间的 manifest，切换 `CURRENT` | **~0**（零额外存储） |
| **单表/单分区恢复** | 只需该分片的 manifest 历史 | ~0 |
| **误删表恢复**（`DROP TABLE` 后悔） | Catalog 保留 tombstone 30 天，`CURRENT` 仍指向旧 schema 与分片 | ~0 |
| **跨 Region 灾备** | 对象存储的跨区复制（CRR） | 存储 + 复制流量费 |
| **逻辑备份**（导出 SQL） | `mysqldump` 协议路径，或 `yb-cli backup` 流式导出 | 扫描带宽 |
| **离线归档** | 生命周期规则把冷对象下沉到归档层 | 归档层单价 |

**对比传统方案**：MySQL 的 PITR 需要"全量备份 + binlog 增量 + 恢复演练"，恢复一次是小时级且需要专门演练。本系统的 PITR 是**改一个指针**，秒级完成，且**可以随时演练**（因为演练不需要真的恢复——只需以历史 manifest 打开一个只读视图）。

**这是对象存储不可变模型带来的第二个重大红利**（第一个是 §1.3 的成本解耦）。

### 12.4 扩缩容

| 操作 | 步骤 | 停机 |
|---|---|---|
| **增加 CN** | 启动进程 → 向 MS 注册 → 加入读负载均衡 | 无 |
| **减少 CN** | 从负载均衡移除 → 若持有租约则主动释放（MS 立即授予他人）→ 进程退出 | 无（主动释放比等超时快得多） |
| **增加分区** | `REORGANIZE PARTITION` → 构建新分片 → 切换指针 | 无 |
| **扩容 MS** | Raft 成员变更（加节点 → 追日志 → 移除旧节点） | 无 |

**优雅关闭协议**（重要，影响 RTO）：CN 在退出前应当**主动释放租约**并通知 MS，这样新写者可以立即接管（RTO ≈ 1 秒），而不是等 TTL 超时（10–20 秒）。这要求 CN 注册 shutdown hook 并有足够的退出宽限期。

```
yb_orphan_objects_total                               # ★ 非零需排查（§6.9）
```

**每查询对象读取数（`yb_query_objects_fetched`）是这个系统最独特的指标**——它是成本与性能的直接代理。应当为每类查询设定预算（§14.2）并在 CI 中做回归门禁。

**接入**：OpenTelemetry（trace + metric）+ Prometheus 端点。慢查询日志记录其对象读取明细，便于定位"为什么这个查询读了 500 个对象"。

## 13. 成本模型

> ⚠️ **本章的所有单价为量级参考，必须在实现阶段按目标云厂商的实时价目表复核。** 本章的目的是建立**成本的结构模型**，而不是给出精确数字——评审应关注结构（哪些成本与数据量绑定、哪些与计算绑定、哪些与请求次数绑定），而非具体小数位。

### 13.1 成本结构分解

这是理解本系统成本优势的关键：**传统方案的绝大部分成本与"实例存活时间"绑定，而对象存储方案的成本与"实际使用量"绑定。**

| 成本项 | 传统方案（ECS + RDS） | YangBase | 绑定对象 |
|---|---|---|---|
| 存储容量 | 云盘，按预配置容量付费（即使没用满） | 对象存储，按实际字节付费 | 数据量 |
| 计算 | 实例按小时付费，**空闲也收费** | CN 可随时停；MS 规格极小 | **存活时间** |
| 请求 | 无此成本项 | **按请求数付费** | 访问次数 |
| 网络 | 内网免费，跨区收费 | 内网免费（同 Region），跨区收费 | 流量 |
| 备份 | 快照按容量收费 | **近乎为零**（历史 manifest 复用） | — |
| 高可用 | 需要多副本实例，成本翻倍 | **由对象存储自带** | — |

**⚠️ 一个必须内化的成本不对称：写在对象存储上比读贵一个数量级。**

| | AWS S3 | 比值 |
|---|---|---|
| `PUT` | $0.005 / 1000 次 | **12.5×** |
| `GET` | $0.0004 / 1000 次 | 1× |

这条不对称是 §6.3.4 组提交设计的**经济依据**，比延迟理由更硬：即使某天 PUT 的延迟降到与本地盘相当，**只要按请求计费，就必须攒批**。它也是 §8.8 "索引与主数据共享同一个 WAL 批次"这一设计的价值来源——如果每个二级索引单独写一次 PUT，写入成本会按索引数线性放大。

> 注：国内厂商（OSS / COS）的请求计费目前是**对称**的（¥0.01/万次，读写同价），但**仍按次计费**，因此上述结论不变。

### 13.2 场景估算

**场景 S1：低频初创应用**（正是本系统的目标场景）

| 参数 | 值 |
|---|---|
| 数据量 | 50 GB |
| 读 | 平均 20 QPS，峰值 100 QPS，缓存命中率 95% |
| 写 | 平均 2 TPS，峰值 20 TPS |
| 表结构 | 10 张表，其中 3 张分区（各 8 个分区） |
| 分片数 | 13 个写入分片 |

**对象存储成本**（按国内某云标准存储的量级估算，同一 Region 内网）：

| 项目 | 计算 | 月成本量级 |
|---|---|---|
| 存储 | 50 GB × ¥0.12/GB/月 | ~¥6 |
| GET | 20 QPS × 5% miss × 86400 × 30 = 2.6M 次 | ~¥3 |
| PUT | 2 TPS，组提交窗口自适应（空闲时近 0）→ 实际约 1 PUT/s → 2.6M 次 | ~¥3 |
| LIST | 后台任务，低频 | <¥1 |
| 网络 | 同 Region 内网免费 | ¥0 |
| **小计** | | **~¥13/月** |

**计算成本**：

| 角色 | 规格 | 月成本量级 |
|---|---|---|
| CN × 1 | 2 vCPU / 4 GiB，按需 | ¥150–250 |
| CN × 1（若用节假日折扣包年） | 同上 | **¥50–80** |
| MS × 3 | 1 vCPU / 2 GiB（可与 CN 合部署复用机器） | ¥0–180 |

**对比：传统 RDS 方案**

| 项目 | 月成本量级 |
|---|---|
| RDS MySQL 高可用版 2核4G | ¥400–700 |
| 云盘 100 GB | ¥30–50 |
| 备份存储 | ¥10–20 |
| 只读实例（若需要） | ¥400+ |
| **小计** | **¥450–800/月** |

**结论（必须表述准确，避免夸大）**：

> 成本优势**不是均匀的 10 倍**，而是分两部分：
> 1. **与数据量绑定的成本降低约 30–50 倍**（数据层从 ¥450–800/月 降到 ~¥13/月）；
> 2. **与计算绑定的成本从"不可中断"变为"可中断、可套利"**——CN 与 MS 都可以随时销毁重建，因此可以完全跟随云厂商的折扣周期迁移，把计算成本压到包年折扣价甚至抢占实例价。
>
> 这两点正是 §0.3 中 G3 的量化展开。**真正的价值在于第 2 点**：它把"续费涨价"从一次被迫的停机搬迁，变成一次"拉起新实例、销毁旧实例"的无状态操作。

**场景 S2：中等规模**（数据 1 TB，读 500 QPS，写 100 TPS）

| 项目 | 计算 | 月成本 |
|---|---|---|
| 存储 | 1024 GB × ¥0.12 | ~¥123 |
| GET | 500 QPS × 10% miss → 130M 次 | ~¥130 |
| PUT | 100 TPS → 组提交后约 10 PUT/s → 26M 次 | ~¥26 |
| CN × 3 | 4 vCPU / 16 GiB | ¥900–1500 |
| **合计** | | **~¥1200–1800** |

对应传统方案约 ¥3000–6000/月。**规模越大，请求成本占比越高**——这正是 §14.2 要把"每查询对象读取数"作为一等指标的原因。

### 13.3 成本控制策略

| 策略 | 手段 | 效果 |
|---|---|---|
| **提高缓存命中率** | 常驻 `.idx`（§6.7）；优化器偏好 covering index（§10.2 R2） | 每降低 1% miss，GET 成本降 1%；**但更关键的是降低延迟** |
| **减少请求数而非字节数** | 组提交（§6.3.4）；块级剪枝（§8.5）；范围读替代整对象读 | 请求费与延迟同时下降 |
| **存储分层** | 生命周期规则把 90 天前的数据下沉到**低频访问层** | 存储单价降 40–70%，且取回免费、延迟可接受 |
| **⚠️ 归档层几乎永远不该用于数据库** | 见下 | — |
| **⚠️ 禁用 Intelligent-Tiering** | 见下 | — |

**为什么归档层不适合数据库**（用数字说话，以 AWS 为例）：

| 项 | 数值 |
|---|---|
| Glacier Instant Retrieval 存储价 | $0.004 /GB-月 |
| Glacier IR **取回**价 | **$0.03 /GB** |
| 即：取回一次的成本相当于 | **存放 7.5 个月** |

也就是说，**只要一个归档对象在 7.5 个月内被读一次，归档就是亏的**。数据库中"永远不会被再读"的数据几乎不存在（备份校验、审计查询、偶发的历史回溯都会触碰它）。因此：

> **存储分层的下界是"低频访问层"，不是"归档层"。** 真正该用来归档冷数据的机制是 §9.4 的 `DROP PARTITION`（成本≈0），而不是把对象下沉到取回昂贵、有解冻延迟的归档层。

**为什么必须禁用 Intelligent-Tiering**：它按**对象数**收取监控费（$0.0025 / 1000 对象-月）。LSM 的一个典型特征是**对象数量多而单个对象小**（WAL 批次、增量 manifest、小 SST）。1 亿个小对象每月的监控费就是 $250，**远超这些对象本身的存储费**。这条对"小对象密集"的存储系统是一个隐蔽的成本陷阱。

**真正有效的低成本归档路径**（按推荐度排序）：

1. **`DROP PARTITION`**（§9.4）：成本≈0，且顺带减少 manifest 体积与读放大；
2. **Compaction 时物理丢弃已过 GC 水位的旧版本**（§6.6）：这本来就会发生，只是要确保水位推进；
3. **下沉到低频访问层**：唯一适合"仍需偶尔读取的冷数据"的选项；
4. 导出为逻辑备份后删除（`yb-cli backup` → 对象存储上的独立归档桶）。
| **`DROP PARTITION` 而非 `DELETE`** | 冷数据按时间分区，直接删分区（§9.4） | 归档成本 ≈ 0，且无写放大 |
| **压缩** | 数据块 LZ4（默认）；可选的 ZSTD 高压缩档 | 减少 40–70% 存储与流量，代价是 CPU |
| **CN 起停** | 低峰期缩到 1 个最小实例；配合 Serverless 按请求拉起 | 计算成本可降到接近 0 |
| **`async` 提交档** | 非关键表使用（§6.3.4） | 降低 PUT 数，代价是 RPO>0 |
| **避免全表 `ANALYZE`** | 从 `.idx` 聚合统计（§10.3） | 统计成本降 1–2 个数量级 |

**一条需要警示的反模式**：不要把对象存储当作"可以随意 LIST 的文件系统"。`LIST` 是分页的、有请求成本的慢操作。**任何在热路径上调用 LIST 的代码都应被视为缺陷**（§3.4）。

## 14. 性能目标与基准

### 14.1 目标 SLO

以下为**设计目标**，不是承诺值；它们的作用是给实现提供验收标尺，并让评审者判断是否与目标场景匹配。

**行业实测参照**（用于校准目标，避免设定物理上达不到的 SLO）：

| 来源 | 实测数据 |
|---|---|
| S3 Standard `GET`（SlateDB 引用） | p50 **14 ms** / p99 **113 ms** |
| S3 Standard `PUT`（WarpStream 实测） | p99 **400–600 ms** |
| turbopuffer（对象存储向量库） | 热 namespace **14 / 27 ms**（p50/p99）；冷 **874 / 1686 ms** |
| Bufstream（Kafka on S3，两阶段提交） | median **260 ms** / p99 **500 ms** |

> **最重要的一个数字是 turbopuffer 的冷热比：约 60 倍。** 这不是实现缺陷，而是"对象存储作为数据层"的物理下界。任何本系统的 SLO 都必须**分成"缓存命中"与"未命中"两栏**来陈述，否则就是在自欺欺人。

| 指标 | 目标（缓存命中） | 目标（未命中/冷） | 说明 |
|---|---|---|---|
| **点查延迟 p50** | ≤ 15 ms | ≤ 60 ms | 未命中 = 1 次 GET |
| 点查延迟 p99 | ≤ 60 ms | ≤ 300 ms | 受 S3 GET p99 ≈ 113 ms 约束 |
| **写提交延迟 p50**（`sync` 档） | ≤ 50 ms | — | S3 PUT p50（14 ms）+ 攒批窗口 |
| 写提交延迟 p99 | ≤ 500 ms | — | 受 S3 PUT p99（400–600 ms）约束 |
| 写提交延迟 p50（`async` 档） | ≤ 2 ms | — | RPO > 0 |
| **单分片写入吞吐** | ≥ 5,000 TPS | — | 组提交后，batch 约 50 |
| 全局写入吞吐（13 分片） | ≥ 50,000 TPS | — | 横向扩展 |
| 范围扫描吞吐 | ≥ 80 MB/s | — | 并行预取；吞吐 ≈ 并发数 ÷ 单请求延迟 |
| 全文检索 top-100 p50 | ≤ 200 ms | ≤ 800 ms | 含 BM25 排序 |
| 分区裁剪后的大表过滤 | ≥ 100× IO 减少 | — | §8.5 的核心卖点 |
| **语义可用性** | 99.9% | — | 扣除对象存储自身 SLA |

**⚠️ 关于冷查询的诚实声明**：上表的"未命中"栏与 MySQL/InnoDB 用户的心理预期相差 **2–3 个数量级**。这不是可以通过优化消除的差距，而是架构选择的必然结果。因此：

- §12.5 的 `yb_query_objects_fetched` 与缓存命中率**必须作为一等监控指标**；
- 必须提供**主动预热**能力——turbopuffer 的做法是暴露 `hint_cache_warm` 与 namespace pinning，让应用在预知流量前主动预热。本系统对应的设计见 §6.7 的"缓存预热提示"；
- 这条差距必须写进用户文档的第一屏，而不是藏在性能章节里。

### 14.2 关键路径 IO 预算（实现验收基准）

这是本文档最应当被**实现为 CI 门禁**的部分：

| 操作 | 对象存储请求预算 | 传输字节预算 |
|---|---|---|
| 主键点查（稳态） | **≤ 1 GET** | ≤ 64 KB |
| 主键点查（冷缓存） | ≤ 4 GET | ≤ 512 KB |
| 索引点查（稳态） | ≤ 2 GET | ≤ 128 KB |
| 小事务提交（组提交，批 50） | ≤ 1 PUT | ≤ 256 KB |
| 只读事务开始 | **0** | 0 |
| 分区裁剪查询（命中 1 个分区） | ≤ 1 GET + 命中块数 | 正比于命中块 |
| **`COUNT(*)`（无谓词，`T=now`）** | **0 GET** | **0** | 
| **`COUNT(*)`（低基数列等值）** | **0 GET** | **0** |
| **`COUNT(*)`（分区表整分区）** | **0 GET** | **0** |
| **`COUNT(*) AS OF 历史时刻`** | ≤ 跨越 `T` 的文件数（通常 0–5） | ≤ 5 × 64 KB |
| 全文检索 top-100 | ≤ 8 GET | ≤ 1 MB |
| `CREATE INDEX`（1 GB 表） | 扫描全部数据 + 写入索引文件 | ~2× 表大小 |
| 新 CN 冷启动到可服务 | ≤ 20 GET | ≤ 8 MB |

**验收方式**：在集成测试中用**带计数的 ObjectStore 装饰器**（`CountingObjectStore`）包裹真实实现，断言每个场景的请求数不超过预算。这比测延迟更可靠——延迟受环境影响大，请求数是确定性的。

```kotlin
class CountingObjectStore(private val delegate: ObjectStore) : ObjectStore {
    val requests = ConcurrentHashMap<String, AtomicLong>()   // op -> count
    val bytes = ConcurrentHashMap<String, AtomicLong>()
    // ... 每个方法委托并计数
}

@Test fun `point lookup 稳态只应产生 1 次 GET`() = runTest {
    val counting = CountingObjectStore(mockStore)
    val engine = openEngine(counting)
    engine.pointGet(pk = 42)      // 预热，填充缓存
    counting.reset()
    engine.pointGet(pk = 43)      // 测量
    assertEquals(1, counting.count("get"))   // ★ 这条断言守护整个存储层设计
}
```

| 基准 | 目的 | 关键指标 |
|---|---|---|
| **sysbench OLTP point-select** | 点查性能 | QPS、p50/p99 延迟、每查询 GET 数 |
| **sysbench OLTP read-write** | 混合负载与提交延迟 | 提交延迟分布、每次提交 PUT 数 |

## 15. 技术选型

### 15.1 语言与运行时

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | **Kotlin 2.x** | 空安全、协程、`value class`（减少装箱）、密封类做状态机、DSL 友好 |
| JVM | **JDK 21+** | 虚拟线程（`Loom`）、`ZGC` 的低停顿、`FFM API` |
| 并发模型 | **协程（对象存储 IO）+ 固定平台线程池（本地缓存引擎）** | 对象存储 IO 是纯异步的，协程的挂起/恢复开销远低于线程；但**虚拟线程对 JNI 阻塞无效**，见下 |

> **⚠️ 一个已经踩过的工程约束：虚拟线程无法卸载被 JNI 钉住的线程。**
>
> RocksDB / Speedb 的 JNI 调用会**钉住（pin）载体线程**，此时虚拟线程无法卸载，`--enable-preview` 的虚拟线程优势归零。Java 24 的 JEP 491 移除了 `synchronized` 造成的钉住，但**原生帧（native frame）造成的钉住依旧存在**。
>
> 因此本项目**不能**用虚拟线程来"隔离"本地缓存引擎的阻塞调用。正确做法是分层：
>
> | 路径 | 并发模型 |
> |---|---|
> | SQL 解析/优化/执行、对象存储 IO | **协程**（挂起时释放线程） |
> | 网络（MySQL 协议、gRPC） | Netty EventLoop + 协程适配 |
> | **本地缓存引擎（RocksDB/Speedb，§6.7 L2）** | **固定大小的平台线程池 + 信号量限流** |
>
> 后者其实也更符合存储引擎作为**稀缺资源**应有的形态（有限并发度 + 显式背压），而不是无限放大并发。
| 序列化 | **Kotlinx Serialization**（元数据）+ **手写二进制**（热路径） | 元数据对象可读性优先；SST/WAL 的格式必须手工控制以精确优化 |

**为什么不用 Kotlin/Native 或 GraalVM native image**：JNI 依赖（RocksDB、压缩库）在 native image 下需要大量配置；JVM 的 JIT 对长时间运行的数据库更有利。保留 GraalVM 作为"减少冷启动"的后续选项。

| 中文分词 | **jieba-analysis** 或 **HanLP** | 可插拔接口（§8.6.4）；**实现现状：没有引入任何一个**，见下 |
| 指标 | **Micrometer + OpenTelemetry** | §12.5 |
| 测试 | **JUnit 5 + Kotest（断言/属性测试）+ Testcontainers（MinIO）** | 对象存储的模拟与故障注入 |
| 基准 | **JMH** | 微基准 |

> **关于中文分词的现状**：实现里只有 `standard` 与 `ngram` 两个分析器
> （`Analyzer.kt`；`WITH PARSER ngram` 走的是 CJK 二元切分的兜底模式，
> 正是 §8.6.4 写的那条兜底路径）。**没有**引入 jieba / HanLP——理由与
> [Analyzer.kt](../yb-index/src/main/kotlin/com/cloudea/yangbase/index/fulltext/Analyzer.kt)
> 的注释一致：不为分词引入外部依赖与词典体积，`FullTextIndex` 只依赖 `Analyzer` 接口，
> 需要真正的分词时实现该接口即可替换。

**刻意不引入的依赖**（及理由）：

| 库 | 不用的理由 |
|---|---|
| **Lucene** | 假设本地文件系统与随机读写；MVCC 集成困难（§8.6） |
| **Calcite** | 其优化器基于"行数/CPU"的代价模型，与本文档 §10.2 的"请求数"模型不匹配；且引入学习成本 |
| **Vert.x MySQL server** | **不存在**。`vertx-mysql-client` 是纯客户端（Netty + `MySQLCodec`），Vert.x 生态没有服务端协议实现。§15.2 中列出的参考实现是 ShardingSphere-Proxy 与 PolarDB-X |
| **一个完整的分布式共识库（如 etcd/raft-java）** | MS 的 Raft 需求很窄（只需日志复制 + 成员变更），可选用成熟实现（如 `jgroups-raft` 或 `sofa-jraft`），但不应引入完整服务发现栈 |

## 16. 风险与开放问题

**本章是评审的重点。** 以下每一项都是我认为**尚未充分解决或需要集体决策**的问题，而不是已经解决的。

### 16.1 已决策事项

> **以下九项已于 2026-09-23 评审确认，作为后续实现的依据。**
> 保留「被否决的方案」一列是为了记录当时的推理，避免日后反复讨论同一问题。

| # | 问题 | ✅ 决定 | 被否决的方案与理由 |
|---|---|---|---|
| **Q1** | 提交延迟 p50 ~40–80 ms 是否可接受？ | **接受，作为产品的明确边界**。出厂默认 `sync`（RPO=0）；`async` 作为**可选**档，需在表级/会话级**显式声明**，并在 `SHOW VARIABLES` 与连接建立时可见 | ❌ 多 CN 间 P2P 复制暂存——会把 CN 变成"轻微有状态"，违反 P5；❌ 默认 `async`——默认 RPO>0 与事务数据库的定位冲突 |
| **Q2** | MS 是否真的值得常驻？ | **双模式，部署时选择**。`MetaServiceClient` 与 `ObjectStoreCoordination`（§4.7）两个实现都交付，由部署者按成本/延迟取舍 | ❌ 只做常驻 MS——失去零常驻成本的部署选项；❌ 只做纯对象存储——每次提交多 1–2 个 RTT 且租约边界情况难测 |
| **Q3** | 租约 TTL 取值？ | **10–15s**（依据 §6.8 的恢复时间估算：恢复需 3–5s，TTL 必须显著大于它，否则会活锁） | ❌ 5s——与对象存储尾延迟量级不匹配，网络抖动导致误判切换、写者颠簸；❌ 60s——故障时写入长时间不可用 |
| **Q4** | 自研倒排索引是否值得？ | **完全自研，M4 交付**。不引入 Lucene/Tantivy 兜底 | ❌ 首版接 Tantivy/Lucene 再替换——引入外部依赖，且它们的"读到即最新"假设与 MVCC 根本冲突（§8.6.5），集成成本未必低于自研 |
| **Q5** | 是否需要 binlog / CDC？ | **提供**。变更流直接基于对象存储上的 WAL（它本来就是不可变、有序、可重放的） | ❌ 不做——放弃与下游数据栈（数仓、搜索、缓存失效）的对接能力，而这项能力的边际成本几乎为零 |
| **Q6** | 构建系统 | **Gradle Kotlin DSL 多模块**（D13） | ❌ Maven——Kotlin 增量编译慢；且 JaCoCo 对 Kotlin 的 inline 函数/属性访问器/when 分支统计偏悲观，会显著增加达成 50% 分支覆盖率的成本 |
| **Q7** | 单分片写入 TPS 天花板是否需要更激进的设计？ | **先用基准验证**（目标 5,000 TPS/分片），不足再优化（如 WAL 分片写入） | ❌ 超前设计——在未验证瓶颈前引入复杂度 |
| **Q8** ⭐ | **默认隔离级别是 RR 还是 RC？** | **默认 RR = 快照隔离**（D12）。**但必须如实报告语义并显式警告与 InnoDB 的差异**，见下 | ❌ 默认 RC——虽然更保守、更少误导，但迁移摩擦大，且本系统的 SI 是语义明确、可证明的隔离级别，不是"假装支持 RR" |
| **Q9** | 2PC 是否采用 Cornus 式方案替代 primary record？ | **primary record**（§7.3），M2 用原型实测验证 | ❌ Cornus `LogOnce()`——需要共享存储的 CAS 原语，且在单写者架构下 primary record 不产生额外网络往返（§7.3 有详细对比） |

#### Q8 的代价：选了 RR 就必须付出的三件事

这个决定背后有一条调研中最值得警惕的发现：

> **Bufstream 通过了 Jepsen 的存储正确性验证，但仍继承了 Kafka 的事务隔离缺陷。**
> 教训是：**"协议兼容"不等于"语义兼容"。** MySQL 用户对 REPEATABLE READ、间隙锁、autocommit 的期望远强于 Kafka 用户。

本设计选择默认 RR，前提是**不与用户玩文字游戏**。快照隔离是语义明确、可证明的隔离级别，不是"假装支持 RR"——但既然名字一样，就必须主动暴露差异，否则一旦用户发现"我的 RR 居然出现写偏斜"，就是口碑灾难。因此以下三件事是**这个决定的一部分，不是可选项**：

| # | 必须做的事 | 落地方式 |
|---|---|---|
| **1** | **如实报告** | `SELECT @@transaction_isolation` 与 `SHOW VARIABLES` 返回 `REPEATABLE-READ` 的同时，必须提供 `@@yangbase_isolation_detail` 之类的扩展变量说明其实现是快照隔离 |
| **2** | **主动警告** | 用户文档**第一屏**（不是性能章节的角落）说明与 InnoDB 的差异：不提供 next-key lock、不防写偏斜、唯一约束需跨分片锁 |
| **3** | **提供迁移检查工具** | `yb-cli analyze-sql <文件>` 扫描应用 SQL，标出依赖 InnoDB 加锁语义的高风险用法，并给出改写建议 |

**若日后发现上述三件事不足以建立信任**，退回默认 RC 的成本很低（只需改默认值与 `@@transaction_isolation` 的返回值），因此这不是一个不可逆的决定。

### 16.2 技术风险

| 风险 | 严重度 | 说明与缓解 |
|---|---|---|
| **R1 对象存储尾延迟** | 高 | p99 可达数百 ms，会传导到用户请求。缓解：请求对冲（hedged request）、提高缓存命中率、`async` 档；**无法根除**，必须作为产品边界承认 |
| **R2 Manifest 一致性的推理链复杂** | **高** | §6.5 中"限频刷新 manifest 仍是安全的"这条推理涉及 MVCC、GC 水位、compaction 三者的交互。**必须有专门的形式化论证与并发测试**，这是最可能出现微妙数据错误的点 |
| **R3 MVCC 与倒排索引 deletes 位图的集成** | 高 | §8.6.5 的"位图带 commit_ts 范围"设计复杂度高，且事后无法补救。建议先做一个独立的原型验证 |
| **R4 自研 FST / WAND 的实现风险** | 中 | 缓解：分阶段交付（Q4），接口预留替换点，先用简单实现保证正确性 |
| **R5 请求成本失控** | 中 | 某个未预料的代码路径在热路径上发起 LIST 或大量小 GET。缓解：`yb_query_objects_fetched` 指标 + CI 门禁（§14.2） |
| **R6 GC 与长事务** | 中 | GC 删除了长事务需要的文件 → 读失败或数据损坏。缓解：保守的 GC 水位（§6.9）+ 活跃读事务的 TTL 租约（§7.1） |
| **R7 Compaction 流量成本** | 中 | 大数据量下的 compaction 会产生可观的流量与请求费用。缓解：compaction 收益预估（§6.6）+ 带宽预算 + 存储分层 |
| **R8 MS 的一致性实现** | 中 | 自己实现 Raft 是经典陷阱。缓解：使用成熟的 Raft 库，MS 的状态机保持极简 |
| **R9 分区键选择不当** | 中 | 用户选了导致大量跨分区事务的分区键 → 性能崩塌。缓解：默认推荐 `HASH(业务主维度)`；提供"跨分区事务占比"的监控指标与告警 |
| **R10 与 MySQL 语义的隐性差异** | 中 | 如自增不连续、SI 不防写偏斜。缓解：§11.3 的显式清单 + 迁移检查工具（扫描 SQL 找出高风险用法） |
| **R11 计数去重的静默错误** | **高** | §8.9.3 的 LSM 多版本去重若出错，`SELECT COUNT(*)` 会**静默返回错误数字**——不报错、不降级、难以察觉，而用户拿它做分页与对账。缓解：**属性测试**（随机写入/删除/compaction 后，元数据计数与全表扫描逐次比对）+ 强制 L1+ leveled 不变式 + 监控"元数据计数与抽样扫描的偏差" |
| **R12 compaction 布局与计数优化的张力** | 中 | §8.9.3 要求 L1+ 必须 leveled，而 leveled 的写放大显著高于 tiered。缓解：先用基准量化 leveled 在本场景下的实际写放大；若不可接受，需重新设计去重（见 §16.3 空白项） |

### 16.3 尚未解决的设计空白

明确列出本文档**没有回答**的问题，避免评审者误以为已覆盖：

1. **多租户与资源隔离**：多个数据库共享同一 MS 与对象存储前缀时的配额、限流、公平性。
2. **权限模型的完整设计**：目前只有 `users.json` 的粗略描述，缺少 `GRANT/REVOKE`、列级权限、`DEFINER` 语义。
3. **跨库 JOIN 与跨库事务**：默认假设单库内操作，跨库行为未定义。
4. **`EXCHANGE PARTITION`、子分区（`SUBPARTITION`）** 的支持范围。
5. **字符集的完整支持矩阵**：目前只列出 4 种，`gbk`、`latin1` 的排序规则差异未细化。
6. **MS 的成员变更与脑裂防护**的具体协议（依赖所选 Raft 库的能力）。
7. **对象存储的凭据轮转**与最小权限的 IAM 策略模板。
8. **大规模 schema 变更**（如修改列类型）的在线迁移方案——目前只覆盖了"加列/删列"这类无重写的场景。
9. **成本模型在超大规模下的验证**（S2 场景的估算尚未经过实测）。
10. **与 Serverless 平台（如 Cloudflare Workers / Vercel）的集成**——CN 能否作为边缘函数运行？对象存储的 R2 无出网费使其有吸引力，但 CN 的内存与缓存层假设不成立。
11. **tiered compaction 与 COUNT 精确性的兼得方案**——D14 为了 §8.9 的计数去重强制了 leveled 布局，代价是更高的写放大。是否存在一种"tiered 布局 + 精确计数"的方案？（例如在 compaction 时维护每个 tier 的"键重叠度"元数据）这是一个值得后续研究的开放问题，**但目前不阻塞实现**。

## 17. 里程碑

每个里程碑都有**可演示的成果**和**可验证的验收标准**，而不是"完成了某个模块"。

### M0 —— 打通端到端（骨架）

**目标**：能用 JDBC 连上，建表，插入，点查。

- `ObjectStore` SPI + 本地 FS 实现 + S3 实现（含能力探测）
- 最小 LSM：MemTable → SST → Manifest（无 WAL，无 compaction）
- MySQL 协议：握手、认证、`COM_QUERY`、文本协议结果集
- `CREATE TABLE` / `INSERT` / `SELECT ... WHERE pk = ?`
- `CountingObjectStore` 测试夹具

**验收**：JDBC 客户端能完成一次完整的建表-插入-点查；`CountingObjectStore` 断言点查 ≤ 1 GET（稳态）。

### M1 —— 可持久化与可恢复

**目标**：CN 被强杀后数据不丢。

- `CoordinationService` 接口 + **两个实现**：`MetaServiceClient`（Raft + TSO + 租约 + Catalog）与 `ObjectStoreCoordination`（§4.7，Q2 决策）
  —— **实现现状**：另有一个单 CN 用的 `SingleProcessCoordination`，且它是 `--coord-mode` 的出厂默认值（见 §4.7 的注）
- WAL：多小对象日志流 + 组提交（`sync` 档，**出厂默认**，Q1 决策）
- 崩溃恢复：新写者接管流程（§6.8）
- Fencing 的四道防线（§4.3）
- 租约 TTL 默认 **10–15s**（Q3 决策），且必须显著大于 §6.8 估算的恢复时间

**验收**：
- 随机时点 `kill -9` CN，恢复后无丢数据；提交延迟 p50 ≤ 50ms（§14.1 校准后的目标）
- **两种协调模式跑同一套并发/故障注入测试并全部通过**（§4.7 的测试要求）—— **实现现状**：`CoordinationConformanceTest` 实际把 **3 种**模式（含单 CN 的 `SingleProcessCoordination`）各跑一遍
- 断言租约 TTL > 恢复时间，否则存在活锁风险

### M2 —— 完整事务与分区

**目标**：能用它写真实的 CRUD 应用。

- MVCC 与快照隔离（§7.1）
- 跨分片 2PC（§7.3）
- 二级有序索引（§8.3）
- 分区：`RANGE`/`LIST`/`HASH` + 分区裁剪（§9.1、§9.2）
- `information_schema` 的完整实现
- `mysqldump` 可用

**验收**：sysbench OLTP read-write 通过；TPC-C 100 仓通过；单分片事务占比 > 90%。

### M3 —— 索引体系与优化器

**目标**：大表查询的 IO 降到可用。

- 跳数索引（minmax / set / bloom / ngrambloom）（§8.5）
- 哈希索引（§8.4）
- **计数索引**（§8.9）—— 五个机制中，**机制 1（manifest 行数）与机制 5（分区级）可提前到 M2**，因为它们只依赖写者与 `stats/`，不依赖 `.idx` 的扩展
- 在线索引构建（§8.7）
- CBO（基于对象存储的代价模型，§10.2）
- 统计信息的 `.idx` 聚合收集（§10.3）

**验收**：
- 一个 10 亿行的分区表上，`WHERE ts BETWEEN a AND b AND status='x'` 的 IO 减少 ≥ 100×
- **`SELECT COUNT(*)` 及其低基数谓词变体做到 0 GET**，且与全表扫描的结果**逐次相等**（属性测试，覆盖 R11）

### M4 —— 全文检索

**目标**：可用的中文/英文全文检索。

- 段结构 + postings 分块（§8.6.1、§8.6.2）
- 分词器：Standard + Chinese(Jieba) + Ngram
- `MATCH ... AGAINST ... IN BOOLEAN MODE`
- FST 词典 + block-max WAND
- `IN NATURAL LANGUAGE MODE` + BM25
- 段合并（§8.6.6）

**验收**：100 万文档的 top-100 检索 p50 ≤ 200ms，且 postings 的读取量 ≤ 全量的 5%。

> **实现现状（2026-09）**：除 **Chinese(Jieba)** 外均已交付——实际只有 `standard` 与
> `ngram` 两种分析器（`Analyzer.kt`），中文检索走 §8.6.4 的 `ngram` 兜底路径，
> 分词器是可插拔接口，替换时不需要动索引结构。理由见 §15.2 的注。

### M5 —— 生产就绪

**目标**：可以托管真实业务。

- `async` 与 `batch` 提交档（§6.3.4）—— 出厂默认仍为 `sync`，`async` 必须显式声明且如实可见（Q1 决策）
- **CDC / 变更流**（Q5 决策）：基于对象存储上的 WAL 提供变更订阅，用于对接数仓、搜索索引与缓存失效
- 存储分层与生命周期规则（§13.3）—— **下界是低频访问层，不得下沉到归档层**
- PITR / `AS OF TIMESTAMP` / `FLASHBACK`（§7.6、§12.3）
- 完整的可观测性（§12.5）

### 附录 C：与相关系统的定位对比

| 系统 | 持久层 | 定位 | 与 YangBase 的关键差异 |
|---|---|---|---|
| **MySQL / PostgreSQL** | 本地块设备 | 单机 OLTP | 无法把数据与计算解耦；扩容需迁移 |
| **Aurora / PolarDB** | 共享块存储（日志即数据库） | 云原生 OLTP | 存储层是**云厂商专有的块服务**，成本仍与容量绑定，且不可跨厂商 |
| **TiDB / OceanBase** | 本地盘 + 多副本复制 | 分布式 HTAP | 需自建多副本，运维复杂，**成本不会随业务低谷下降** |
| **OceanBase Bacchus**（VLDB'26）⭐ | **对象存储** | 分布式 OLTP | **最接近本设计的生产系统**：LSM + 对象存储 + 共享日志服务（PALF 三副本）+ **每 log stream 一个 SSWriter 串行化对象存储写**。成本降 59%(OLTP)/89%(OLAP)。其论文自陈的局限正是 §0.3 的 N1：*对象存储延迟/IOPS 限制小操作频繁的场景* |
| **Snowflake / Databricks** | 对象存储 | 云数仓 / OLAP | 列存、批处理导向，**不提供低延迟事务与 MySQL 协议** |
| **Neon / Lakebase** | 对象存储（pageserver + safekeeper） | Serverless PG | ⚠️ **对象存储不在热路径上**：compute **从不直读 S3**，由 pageserver 代理。本设计（CN 直连对象存储）比它激进得多，延迟风险更高。>98.5% 缓存命中，但 pageserver 层带来约 7× 空间放大 |
| **SlateDB** | 对象存储 | 嵌入式 LSM **库** | 是库而非数据库；不提供 SQL、事务、协议、索引。**仍为单写多读**，多写者需上层自建 |
| **Cornus**（PVLDB'16） | 共享存储 | 分布式事务 | 对 2PC 的关键批评：**协调者关键路径上有"一次网络往返 + 两次 eager 日志写"**；解法是用单个 CAS 原语 `LogOnce()` 消除协调者决策日志。本设计 §7.3 采用 primary record 而非 Cornus 方案，取舍见 §16.1 |
| **SlateDB** | 对象存储 | 嵌入式 LSM **库** | 是库而非数据库；不提供 SQL、事务、协议、索引 |
| **turbopuffer / Chroma** | 对象存储 | 向量/全文检索服务 | 单一用途，无通用事务与 SQL |
| **WarpStream / Bufstream** | 对象存储 | Kafka 兼容的流平台 | 日志语义，非事务数据库 |
| **YangBase** | **对象存储** | **分布式 TP 数据库** | 全部元数据/索引/数据在对象存储；MySQL 协议；多模索引；计算完全无状态且可套利折扣实例 |

**YangBase 的定位可以一句话概括**：

> 面向**低频、读多写少、需要事务与 SQL** 的应用，提供"数据层成本与计算成本彻底解耦"的数据库。
> 它不试图在性能上击败本地盘数据库，而是把"**在没有客户的时候，仍然要为数据库付一笔不便宜的固定费用**"这个问题彻底消解掉。

## 评审关注点速查

以下 9 条**一旦确定就极难更改**。§16.1 的九项已于 2026-09-23 确认，下面这些是**在实现过程中仍需持续守护**的设计前提：

1. **§5.1 对象存储布局** —— 键结构上线后无法迁移。
2. **§5.2 规则 2（索引与数据分离）** —— 违反它将摧毁点查性能的前提。
3. **§6.5 Manifest 一致性的推理链** —— 最可能出现微妙数据错误的点（风险 R2）。
4. **§6.3.4 提交延迟的三档设计** —— 出厂默认 `sync`、`async` 必须显式声明（Q1）。
5. **§7.4 + §16.1 Q8 的三件必做事** —— 如实报告、主动警告、迁移检查工具。**少做任何一件，默认 RR 的决定就不成立。**
6. **§8.6.5 MVCC 与倒排索引的集成方式** —— 事后无法补救（风险 R3）。
7. **§9.3 分区即分片** —— 决定了系统的扩展模型与用户的使用方式。
8. **§3.3.1 CAS 与低延迟的分层解耦** —— 决定了能否同时拿到低延迟与正确性。
9. **§8.9.3 计数去重 + D14 leveled 约束** —— **最危险的静默错误点**：出错时 `COUNT(*)` 返回错误数字但不报错（不降级、不报错，而用户拿它做分页和对账）。
